# Table Detection and Structure Recognition

## What are the separate tasks in table extraction, and what should a pipeline return?

### Takeaway
Treat table extraction as a sequence of related but separately measurable problems: detect table regions, reconstruct the logical grid/cells, recover cell text, and analyze cell roles such as headers. This decomposition supports a hybrid pipeline: native PDF geometry first when available, visual learned inference as a fallback or parallel proposal source, then explicit text alignment and conservative role classification.

### Cited Findings
- PubTables-1M explicitly decomposes table extraction into table detection (locating the table), table structure recognition (recovering rows, columns, and cells), and functional analysis (identifying roles such as headers); it trains/evaluates detection separately from joint structure and functional analysis. [PubTables-1M paper](https://openaccess.thecvf.com/content/CVPR2022/papers/Smock_PubTables-1M_Towards_Comprehensive_Table_Extraction_From_Unstructured_Documents_CVPR_2022_paper.pdf)
- PubTables-1M’s TSR representation includes table, row, column, column-header, projected-row-header, and spanning-cell classes. Intersections of row and column bands define an implicit fine grid, allowing the representation to distinguish cell spans from ordinary cells. [PubTables-1M paper](https://arxiv.org/html/2110.00061v3)
- Table Transformer (TATR) provides separate DETR models for full-page table detection and table structure recognition on table crops; the official inference flow supports supplying recognized word boxes/text to associate text with the predicted structure. [Official Microsoft repository](https://github.com/microsoft/table-transformer); [Hugging Face model documentation](https://huggingface.co/docs/transformers/en/model_doc/table-transformer)
- TableFormer predicts structure tokens and cell bounding boxes from an image; its paper describes obtaining cell text from programmatic PDF sources or OCR and aligning that text with predicted cells. The supplementary material explicitly notes that its predictions alone omit cell content and can have box inaccuracies. [CVPR paper](https://openaccess.thecvf.com/content/CVPR2022/html/Nassar_TableFormer_Table_Structure_Understanding_With_Transformers_CVPR_2022_paper.html); [supplementary material](https://openaccess.thecvf.com/content/CVPR2022/supplemental/Nassar_TableFormer_Table_Structure_CVPR_2022_supplemental.pdf)
- PubTables-1M labels column headers and projected row headers, but its authors say complete row-header labeling for functional analysis is outside the paper’s scope; its header labels are not a universal semantic schema for every document type. [PubTables-1M paper](https://arxiv.org/html/2110.00061v3)
- This repository already has a useful geometry-aware starting point: `parsing/models.py` defines normalized page-coordinate `BBox`, `ParsedElement` with source/confidence/attributes, and page-scoped elements; `parsing/pdf.py` extracts native PDF table cells with row/column attributes, plus a conservative alignment heuristic for simple unruled tables. That file also documents that this parser does not structure image-only/scanned tables. [Repository: models.py](../../src/fastdocparse/parsing/models.py); [Repository: pdf.py](../../src/fastdocparse/parsing/pdf.py)

### Inferences
- Preserve these stages as separate outputs, even if an orchestrator runs them in one call. It makes it possible to identify whether an error came from a missed table, wrong grid, OCR/text assignment, or header interpretation, and to add a model without replacing native PDF extraction.
- Suggested incremental pipeline for this repository:
  1. Detect page modality and retain native PDF text/word geometry where present; render pages/crops for visual detection when appropriate. Do not treat an OCR text-only fallback as equivalent to geometry-preserving parsing: current `ingestion/pdf_ingest.py` and `ocr_engine.py` return text strings and reduce OCR detections to rough line grouping / optional x-prefixes. [Repository: pdf_ingest.py](../../src/fastdocparse/ingestion/pdf_ingest.py); [Repository: ocr_engine.py](../../src/fastdocparse/ocr_engine.py)
  2. Generate candidate table boxes using PDF vector lines/rectangles and text-alignment strategies; retain candidate provenance and scores. Add learned full-page detection (e.g. TATR) as an optional proposal path for image/scanned or difficult pages, not as a universal replacement.
  3. Recover rows, columns, cell boxes, and spans; combine visual structure with native PDF text or OCR words by geometry. Preserve raw text and empty grid cells; distinguish a true spanning cell from a blank cell.
  4. Add functional/header labels as a later, optional layer. Store labels as roles (column header, row header, projected section header, data, footnote/unknown) with evidence and confidence; do not convert uncertain headers into fixed semantic column names.
  5. Link likely continuation tables across pages only after per-page extraction, using compatible column geometry/count, repeated header/content, table title/continuation cues, and adjacent page position. Keep links probabilistic and preserve each page fragment’s local coordinates.
- A suitable output should make a table a page-local object with: document/table/fragment identifiers; page number; table and cell boxes in normalized page coordinates plus page dimensions/units; row/column indices; `row_span`/`column_span`; raw and normalized text with token/word references; separate detection, structure, text, and role confidences (or explicit unknown); source/provenance such as PDF vector, PDF text, OCR, heuristic, or model name/version; and optional cross-page continuation links. Retaining source boxes and transform/render metadata makes detections auditable and maps crops back to page coordinates. This is a design recommendation grounded in the coordinate-preserving models already present here and the box-rich annotations used by PubTables-1M. [Repository: models.py](../../src/fastdocparse/parsing/models.py); [PubTables-1M repository](https://github.com/microsoft/table-transformer)
- In this repository specifically, current native table cells have row/column indices but no explicit span fields, and cell confidence is generally unset; inferred unruled cells are derived from positional ordering and may not share a stable column grid. These are incremental schema gaps, not reasons to discard the current parser. [Repository: pdf.py](../../src/fastdocparse/parsing/pdf.py)

### Gaps
- The repository’s synthetic-customs corpus has no accompanying table ground-truth annotations in the inspected file set. A meaningful numeric benchmark requires a manually checked, versioned annotation set and an agreed policy for blank, merged, and semantically ambiguous cells.
- No general source provides a reliable rule for deciding that two page-local tables are the same continuing logical table; continuation needs task-specific cues and explicit evaluation.

## How do geometry/PDF-native methods compare with learned models, including domain limits and failure modes?

### Takeaway
PDF-native geometry is cheap, explainable, and often strongest on born-digital ruled tables; text-alignment heuristics extend coverage to unruled tables but become ambiguous. Vision models handle raster/scanned pages and visual cues that are absent from the text layer, but their benchmark performance is domain-dependent, cell text may require separate OCR/PDF text alignment, and model outputs can misplace boundaries or mishandle unusual layouts.

### Cited Findings
- PyMuPDF `Page.find_tables()` supports line-based strategies, strict line strategies, and text-position strategies; its documentation notes that borderless tables may fail under line detection, while text positions can generate virtual row/column boundaries. It also warns that backgrounds-only layouts and unusual constructions can be difficult. [PyMuPDF `Page.find_tables()` documentation](https://pymupdf.readthedocs.io/en/latest/page.html); [PyMuPDF FAQ](https://pymupdf.readthedocs.io/en/latest/faq/index.html)
- pdfplumber likewise distinguishes graphical-line and text-alignment strategies and documents visual debugging. Its README states that it works best on machine-generated rather than scanned PDFs. [Official pdfplumber repository](https://github.com/jsvine/pdfplumber)
- The current `parsing/pdf.py` uses PyMuPDF table finding and a page-local unruled-table heuristic. The heuristic requires repeated aligned multi-column rows and has domain-specific row-content tests (e.g., numeric values), so it should not be assumed to detect arbitrary borderless tables. [Repository: pdf.py](../../src/fastdocparse/parsing/pdf.py)
- PubTables-1M is large (nearly one million tables) but derived from scientific articles in PubMed Central Open Access; its paper explicitly says its canonicalization algorithm is designed for PMCOA annotations and identifies extension to other domains as future work. [PubTables-1M paper](https://arxiv.org/html/2110.00061v3); [Microsoft Research project page](https://www.microsoft.com/en-us/research/publication/pubtables-1m)
- TableFormer evaluates across scientific PubTabNet, financial FinTabNet, and general-domain TableBank, but its authors note that public datasets are skewed toward simpler tables/fewer rows and columns, have limited style variance, and may have domain-restricted content. Its reported accuracy is tied to those datasets and protocols, not a guarantee for arbitrary documents. [TableFormer CVPR paper](https://openaccess.thecvf.com/content/CVPR2022/papers/Nassar_TableFormer_Table_Structure_Understanding_With_Transformers_CVPR_2022_paper.pdf)
- TableFormer’s visual model predicts structure and boxes, but the paper’s supplementary material describes subsequent PDF-text matching and box correction because predictions can omit content and have occasional box inaccuracies. [TableFormer supplementary material](https://openaccess.thecvf.com/content/CVPR2022/supplemental/Nassar_TableFormer_Table_Structure_CVPR_2022_supplemental.pdf)
- The official TATR repository describes it as a model for PDFs and images and releases distinct detection and structure checkpoints. Its standard structure model is trained on PubTables-1M; the repository also lists a FinTabNet-trained structure model, evidence that dataset/domain choice is material. [Official TATR repository](https://github.com/microsoft/table-transformer)
- The TATR repository was archived by Microsoft on 2026-09-21 (read-only status shown by GitHub), so pin versions/checkpoints and plan for a maintenance or replacement strategy rather than assuming upstream active support. [Official repository](https://github.com/microsoft/table-transformer)

### Inferences
- Use a modality- and evidence-aware hybrid rather than a single winner: native PDF cells/text when available; vector geometry for ruled structures; text alignment for unruled structures; visual detector/structure model for image tables, scanned pages, or low-confidence native results; then align all cell text from the best available PDF text/OCR source.
- Useful failure-mode checklist for implementation and review:
  - **Rule noise / phantom grids:** page borders, shaded rectangles, stamps, logos, and partial rulings can be mistaken for table edges; strict line modes, crop-local analysis, and alternate proposals help, but may also omit valid cell borders.
  - **Unruled ambiguity:** nearby prose, unequal whitespace, ragged columns, wrapped/multiline text, and right-aligned numbers defeat naïve row/column clustering; line-count and start-x heuristics can create false tables or split a cell into rows.
  - **Merged cells and empty cells:** a merged header may look like several blank grid slots, and empty cells have little/no visual/text evidence. A flat list of cells or a dense CSV cannot faithfully preserve spans; grid and span annotations are needed.
  - **Headers/roles:** multi-row hierarchical headers, row labels, section rows, footnotes, and repeated header rows can be mistaken for data or vice versa. Header inference from location/style alone is uncertain; keep role classification separate from table geometry and allow `unknown`.
  - **Scans/OCR:** raster pages have no PDF text layer, while OCR can introduce character mistakes, missed glyphs, drifted boxes, skew/rotation issues, and reading-order confusion. In the current ingestion route, the text fallback cannot by itself provide cell-level page boxes.
  - **Page continuation:** repeated headers can be mistaken for duplicate data; tables may continue with altered headers, split rows, or multi-level headings. Independent page-level extraction cannot determine logical linkage without document context.
  - **Model shift:** scientific-document visual conventions, fonts, languages, density, and page layouts differ from forms, customs documents, receipts, archival scans, and hand-drawn tables. Strong in-domain scores do not imply universal accuracy.
- This repository’s `synthetic-customs-docs` corpus is useful as a first operational slice, not a diverse-document benchmark: inspection found 36 PDFs, mostly born-digital customs/invoice/packing-list-like documents, with 6 scan-named files (three one-page and three two-page), and 12 two-page documents overall. This gives some digital/scanned and page-boundary cases, but not broad domain, language, table-style, or handwritten-table coverage. [Corpus directory](../../synthetic-customs-docs); counts were checked from the PDFs with PyMuPDF during this research.
- Recommended incremental order: (1) benchmark current native `find_tables` and heuristic behavior; (2) add a proposal/fallback interface and OCR word boxes for scans; (3) standardize spans, cell indices, confidence, and provenance in output; (4) add visual detection/TSR model behind an optional dependency; (5) only then add cross-page linking and richer functional analysis. This keeps model/runtime cost optional and avoids making a scientific-domain checkpoint a hard dependency.

### Gaps
- No retrieved official model documentation establishes expected accuracy for the repository’s customs/invoice-like forms, multilingual scans, or the specific continuation cases in this corpus. It must be tested locally.
- Published headline scores across PubTables-1M, PubTabNet, FinTabNet, and TableBank use different data, annotation policies, and metrics; they are not directly comparable as a universal ranking.

## What evaluation strategy and metrics fit the synthetic-customs-docs corpus?

### Takeaway
Create a small but carefully annotated, document-disjoint benchmark that reports detection, structure, text, header-role, and continuation quality separately, with per-condition slices. Use GriTS topology/content/location plus strict span-aware exact checks for structure, and IoU-based detection precision/recall; do not let one aggregate score conceal a weak scan or merged-header slice.

### Cited Findings
- GriTS compares predicted and gold tables as matrices and supplies topology, content, and location variants (GriTS-Top, GriTS-Con, GriTS-Loc), enabling separate assessment of cell relationships, text, and geometry. The paper describes a polynomial-time heuristic for the underlying 2D most-similar-substructures problem. [GriTS paper](https://arxiv.org/abs/2203.12555); [Microsoft Research summary](https://www.microsoft.com/en-us/research/publication/grits-grid-table-similarity-metric-for-table-structure-recognition/)
- The official TATR repository implements object-detection AP/AP50-style measures for table detection and structure object detection, and GriTS for table structure evaluation. [Official TATR evaluation instructions](https://github.com/microsoft/table-transformer)
- ICDAR cTDaR evaluates table-region detection using polygon IoU and precision/recall/F1 at several IoU thresholds, and recognition by matching cell polygons with IoU thresholds; it includes modern and archival/noisy-table settings. [Official cTDaR evaluation page](https://cndplab-founder.github.io/cTDaR2019/evaluation.html); [competition paper](https://ieeexplore.ieee.org/document/8978120)
- PubTables-1M contains full-page detection annotations and detailed cell/row/column boxes, words, and functional annotations, illustrating why both region-level and cell/grid-level ground truth are needed for separate task measurement. [Official TATR repository](https://github.com/microsoft/table-transformer)
- PubTables-1M notes dataset-specific annotation noise and canonicalization choices, including incomplete source header markup and inferred corrections. This means evaluation requires a consistent annotation policy and canonicalization for both predictions and gold. [PubTables-1M paper](https://arxiv.org/html/2110.00061v3)

### Inferences
- **Sampling / split:** annotate every table occurrence in a manageable initial subset, or stratify intentionally across all 36 PDFs. Split by document/template family (not page or table fragment) to prevent near-duplicate generated layouts leaking into test results. Keep an untouched test subset; tune heuristics/thresholds only on development data. Report document and table counts with each score.
- **Gold annotation fields:** page/table box; all logical rows/columns; each cell’s text, box, row/column index and spans; blank cells; column-header/row-header/projected-section-header/data/footnote/unknown roles; scan/modality and continuation-link labels. Decide whether visual empty grid positions are represented as empty cells and apply the policy consistently.
- **Detection:** use one-to-one table matching at IoU thresholds such as 0.5 and 0.75 (and optionally a threshold sweep), then precision, recall, F1, and average precision. Include false-positive table proposals and pages with no tables. For a compact initial corpus, include per-document macro averages alongside table-weighted totals so a file with many cells does not dominate.
- **Structure:** report GriTS-Top for topology/span recovery, GriTS-Loc for cell geometry, and GriTS-Con for content-aware matching; add strict exact-table accuracy and span-aware cell precision/recall/F1 because GriTS is a soft similarity and a high average can still hide a critical merged-cell error. Report row/column count error and exact `row_span`/`column_span` accuracy explicitly.
- **Text/OCR:** measure cell text exact match and normalized edit distance or CER/WER after a geometry-aware cell assignment; report OCR-only character quality separately from cell assignment to separate recognition mistakes from structure mistakes. Keep a raw-string and a declared normalization policy (Unicode, whitespace, line breaks, decimal separators) to avoid scoring ambiguity.
- **Functional analysis:** role-wise precision/recall/F1 and macro-F1 for header/row-header/section/data/footnote/unknown; optionally evaluate header hierarchy as parent-child relations. Avoid scoring semantic column names as correct unless the dataset provides explicit canonical labels.
- **Continuation:** pairwise continuation-link precision/recall/F1, plus a separate measure of fragment stitching correctness (missed/duplicated rows and repeated-header handling). Report this only if the annotation set includes cross-page logical-table identities.
- **Confidence/provenance:** if the pipeline emits scores, assess reliability with confidence bins/reliability diagrams or expected calibration error and measure error-detection precision/recall at review thresholds; record results by source path (PDF geometry, heuristic, visual model, OCR) to find which path causes errors. Confidence calibration is a recommendation, not a standard metric mandated by the cited papers.
- **Slices and error review:** separate digital ruled, digital unruled, scan/OCR, multi-page, header-heavy/merged-span, and low-resolution/rotated cases. Manually inspect all high-severity failures (missing/extra table, wrong row/column assignment, span loss, page mapping) and maintain a categorized error log. Since this corpus is generated/customs-oriented and small, report uncertainty and sample counts; do not claim broad external validity.

### Gaps
- The corpus inventory gives document/page modality but does not establish how many distinct tables, ruled versus unruled cases, merged cells, or continuation tables it contains. Those distributions should be measured after annotation rather than presumed from filenames.
- A single benchmark split cannot support precise claims about generalization across document domains with 36 mostly related files. Broader external test sets would be needed for that claim.
