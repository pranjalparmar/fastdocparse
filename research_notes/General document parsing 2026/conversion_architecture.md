# General-purpose document conversion architecture

## What do production-oriented converters show about pipeline architecture, and should fastdocparse integrate or build?

### Takeaway

Production document conversion is best treated as a staged pipeline: source-aware extraction, page/region analysis, structure and relation assembly, then separate serialization and downstream chunking. For fastdocparse, the evidence favors building and owning a small, stable canonical representation and orchestration contract while integrating mature parsers, OCR engines and learned models as optional backends; neither a single text-only path nor a mandatory heavyweight converter is a good fit for every user.

### Cited Findings

- Docling's technical report describes a linear pipeline: a PDF backend extracts positioned text and renders page images; page-level AI models add layout and table structure; post-processing aggregates pages, enriches metadata, infers reading order, and assembles a typed document for JSON or Markdown serialization. The report explicitly presents the model pipeline as customizable/extensible. [Docling Technical Report, arXiv:2408.09869](https://arxiv.org/abs/2408.09869); [full report](https://arxiv.org/html/2408.09869v5)
- Docling deliberately offers more than one PDF backend: its report describes a qpdf-based `docling-parse` backend as its default and pypdfium as an alternative, noting trade-offs in speed, memory and table quality. This is a concrete precedent for backend substitution rather than assuming one PDF library is universally best. [Docling Technical Report, §3.1 and §4](https://arxiv.org/html/2408.09869v5)
- The Docling report's default path combines PDF text/token positions with rendered page imagery; its layout detector proposes regions that are intersected with PDF text, while TableFormer structure predictions are matched back to PDF cells to avoid re-transcribing table text. The report notes CPU table processing can take 2–6 seconds depending on cell count, while its OCR path (EasyOCR at high page resolution in that report) can be much slower on CPU. [Docling Technical Report, §3.2](https://arxiv.org/html/2408.09869v5)
- Docling's current documentation describes `DoclingDocument` as a unified Pydantic representation for text, tables, pictures, key-value items, body/furniture trees, groups, layout bounding boxes and provenance. Its document hierarchy stores reading order in ordered tree children. [Docling Document](https://docling-project.github.io/docling/concepts/docling_document/)
- Unstructured uses format-specific `partition` functions to produce typed elements and then performs chunking as a separate step over those elements. Its documentation emphasizes preserving complete semantic elements unless an element itself exceeds the size cap, with original elements retained as metadata when chunks combine them. [Unstructured partitioning overview](https://docs.unstructured.io/open-source/core-functionality/partitioning); [chunking](https://docs.unstructured.io/open-source/core-functionality/chunking)
- MinerU 4.1 documents a shared document model with separate intermediate model/middle JSON and consumer-facing renderings (Markdown, HTML, LaTeX, DOCX, PDF, structured content and content lists). It explicitly warns that a renderer's capability is not automatically exposed by every CLI/API entrypoint, an important distinction between internal model, serialization and product contract. [MinerU output format and result contract](https://opendatalab.github.io/MinerU/reference/output_files/)
- GROBID is a mature, specialized alternative for scientific and technical publications: it parses PDF into structured TEI/XML, provides coordinates, APIs and batch processing, and explicitly focuses on bibliographic metadata and scholarly-document structures rather than arbitrary business forms. [GROBID Introduction](https://grobid.readthedocs.io/en/latest/Introduction/)
- LayoutParser's contribution is a toolkit and shared interface for applying, customizing and sharing document-image-analysis models and pipelines, rather than one fixed end-user conversion pipeline. [LayoutParser paper, ICDAR 2021](https://arxiv.org/abs/2103.15348)
- The repository currently positions fastdocparse as a lightweight, text-first extractor for semi-structured documents, with deterministic per-field grounding/confidence and no required vision-LLM stage; its README identifies complex multi-column layouts and handwriting as weaker cases. The current PDF inspection path extracts native positioned text and tables, and says scanned-PDF OCR is not yet connected to that command. [Project README](../../README.md)
- The repository already has a geometry-aware starting representation: normalized `BBox`, recursive `ParsedElement`, provenance/source, confidence, attributes and page-scoped parsed output; the PDF parser emits block/line/word and table/cell structures. The adjacent research notes identify stable IDs and explicit relations/order metadata as the most direct schema extensions. [Layout research note](layout_methods.md); [table research note](table_methods.md); [models.py](../../src/fastdocparse/parsing/models.py); [pdf.py](../../src/fastdocparse/parsing/pdf.py)

### Inferences

- Own the canonical IR, evidence/provenance rules, stable IDs and versioned public contract; treat PDF extraction, OCR, layout detection, table recognition and domain-specialized parsers as pluggable producers of evidence. This preserves fastdocparse's value proposition and gives later backends a common destination.
- Build on established components rather than training a general layout model or writing a new OCR engine. First benchmark the existing native-PDF path and evaluate Docling as an optional conversion adapter on representative repository documents; separately evaluate OCR backends and specialist tools (for example, GROBID only for scholarly PDFs). Integration should be decided by quality, latency, dependency footprint, licensing, operational support and output fidelity on the target corpus, not by feature lists alone.
- Keep optional dependencies and tiers explicit: native-text extraction as the lightweight baseline; OCR/visual layout/table models as extras; specialist document-family adapters as opt-in integrations. A user should not need GPU/model downloads merely to extract fields from a clean invoice PDF.
- Avoid treating Docling's `DoclingDocument`, Unstructured `Element` objects, MinerU's protocol or Markdown as the fastdocparse public schema. They are useful interoperability targets and design references, but tying the core contract to one project's types, model lifecycle or version cadence would couple parser semantics to an external implementation.
- Preserve a route/diagnostics record per page and derived element: native text, OCR, model, heuristic, tagged structure, or merged evidence. This provides an audit trail when two backends disagree and allows fallback/reprocessing without losing original evidence.
- Establish a small, document-disjoint gold set before selecting an engine. Include business forms, invoices/statements, reports, multi-column prose, tables, graphics, born-digital and scanned/hybrid PDFs. Existing layout research warns that scientific-paper-trained datasets do not establish broad coverage of invoices, receipts, handwriting or scans. [Layout research note](layout_methods.md)

### Gaps

- No independent, directly comparable end-to-end benchmark was located that ranks Docling, Unstructured, MinerU, GROBID and fastdocparse on the repository's target mix, including accuracy, latency, memory, dependency/install burden, licensing and maintenance cost. Vendor-published results should not substitute for a local head-to-head test.
- Docling's technical report is version 1.0 (2024); its current documentation has evolved. Architecture findings from the report describe that reported pipeline, while the current documentation should be consulted for current behavior and options. [Report](https://arxiv.org/html/2408.09869v5); [current documentation](https://docling-project.github.io/docling/)
- Public documentation does not settle which optional engines have the best long-term maintenance/security profile for this project's packaging model. Pinning, license review, model asset provenance and dependency-update policy require separate engineering evaluation.

## What canonical representation best preserves hierarchy, reading order, tables, figures, links and evidence across document classes?

### Takeaway

Represent the source as page-local evidence elements plus hierarchy and typed relations, not as a single string with coordinates attached. Keep source order and physical geometry intact, represent reading order as a derived projection over potentially branching/ambiguous flows, and preserve tables and figures structurally even when a requested text export cannot express all their features.

### Cited Findings

- Docling's document model separates content items (`texts`, `tables`, `pictures`, `key_value_items`) from content-structure trees (`body`, `furniture`, `groups`); items can refer to parents/children, and ordered children in the body tree encode reading order. It also records bounding boxes and provenance where available. [Docling Document](https://docling-project.github.io/docling/concepts/docling_document/)
- Docling's technical report assembles per-page predictions into a typed document and post-processes reading order, figure-caption matches, document metadata and language. In the report's examples, figure text is dropped from Markdown while captions remain and are linked to figures in JSON; header/footer elements can be suppressed in Markdown while remaining structural content. [Docling Technical Report, §3.3 and Appendix](https://arxiv.org/html/2408.09869v5)
- Docling's serialization documentation states that its internal table grid preserves row/column spans. JSON, HTML and OTSL-based formats can retain span information, while Markdown and the documented LaTeX serializer flatten spans because those output formats do not represent them natively. [Docling Serialization](https://docling-project.github.io/docling/concepts/serialization/)
- Docling's chunking abstractions operate directly on the structured document as an alternative to exporting Markdown and chunking afterward. Its hierarchical chunker emits element-based chunks with relevant headers/captions; its hybrid chunker tokenizes and then splits oversized or merges compatible small chunks. [Docling Chunking](https://docling-project.github.io/docling/concepts/chunking/)
- The 2024 reading-order study models immediate succession as a directed acyclic relation and general precedence as its transitive closure; it argues complex pages may have multiple valid flows and reports non-linear order in 23.76% of segments in its ROOR sample. [Zhang et al., EMNLP 2024](https://aclanthology.org/2024.emnlp-main.540/)
- PyMuPDF warns that extracted text can follow PDF coded/content-stream order rather than natural reading order. Its top-left-to-bottom-right `sort` option is a heuristic; positioned blocks and words provide geometry for more informed reconstruction. [PyMuPDF text extraction recipes](https://pymupdf.readthedocs.io/en/latest/recipes-text.html)
- PubTables-1M includes table, row, column, cell, header and projected-row-header annotations, including blank cells and coordinates; its authors address oversegmentation and annotation consistency through canonicalization. Table Transformer separates table detection and structure recognition and aligns recognized words with predicted structures. [PubTables-1M](https://arxiv.org/abs/2110.00061); [Microsoft Table Transformer](https://github.com/microsoft/table-transformer)
- GriTS compares tables as matrices and separates topology, content and location measures, reinforcing the value of preserving a two-dimensional grid rather than irreversibly flattening to CSV or prose. [GriTS](https://arxiv.org/abs/2203.12555)
- Cloud APIs provide production precedents for typed relationships: AWS Textract, for example, links key and value blocks using explicit relationship structures, while Azure's layout model describes polygons/spans and nested table cells. These are vendor schemas, not universal standards. [AWS AnalyzeDocument API](https://docs.aws.amazon.com/textract/latest/dg/API_AnalyzeDocument.html); [Azure layout model](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout)
- Existing project research notes that DocLayNet selected visually identifiable layout labels and avoided many text-semantic, domain-specific roles; the same work discusses ambiguity in segmentation boundaries. The notes recommend generic elements and explicit links for captions, key/value pairs and table membership. [Layout research note](layout_methods.md)

### Inferences

- A compact extensible internal contract should include:
  - `Document`: source metadata, parser/version/configuration, pages and document-level diagnostics.
  - `Page`: stable page index, source width/height, coordinate units/frame, rotation and optional rendered-image reference.
  - `Element`: stable ID; open or extensible type; page-local bbox/polygon; text or asset reference; parent/child links; source order; provenance; confidence; and raw/backend attributes.
  - `Relation`: source/target IDs, typed relation, confidence and provenance. Initial types might include `contains`, `precedes`, `caption_of`, `key_for`, `table_cell_of`, `continues_on_page`, `repeats_header`, and `associated_with`; unknown relations remain possible.
  - `Table`: ordered rows/cells or a grid with row/column indices, spans, cell boxes and text/token references; blank cells are represented explicitly where the grid supports them.
  - `Figure`/graphic: retain a crop or source-asset reference, bbox and optional caption/description links. Do not discard an image just because text extraction cannot interpret it.
- Store raw PDF/object order separately from inferred reading order. A consumer-friendly sequence can be computed from a partial-order graph with deterministic tie-breaking, but keep alternatives/conflicts and mark the linearization as derived rather than authored fact.
- Preserve page-coordinate evidence with coordinate-frame metadata and transformation provenance (PDF points vs normalized coordinates vs rendered pixels). Convert between frames explicitly; a bbox without its page size/origin/rotation is not safely reusable evidence.
- Keep semantic interpretation layered. A generic layout parser may identify a text region, label candidate or table header, but should not turn it into `invoice_number` or `vendor_name`; those task fields belong in the extraction schema and should link back to supporting elements/spans.
- Treat each serialization as a lossy or lossless view with documented behavior. JSON/internal IR should be the round-trip representation; Markdown is a convenient LLM-facing projection; HTML is often a better readable table projection where spans matter; image assets or multimodal references preserve graphic evidence. Do not imply Markdown alone is a lossless archive.
- Return evidence references with extraction results: element IDs and, where available, source token spans and page boxes. This complements fastdocparse's existing deterministic string grounding with visual/page-level grounding while leaving the original source text available for verification.
- Version the schema and use capability/provenance annotations rather than requiring every backend to populate every field. `unknown`, absent and unsupported should be distinguishable from a negative detection.

### Gaps

- There is no single widely adopted interchange format found that unifies native PDF tokens, OCR words, image regions, logical hierarchy, reading-order alternatives, table grids, assets and confidence/provenance. Docling, Unstructured and MinerU expose useful but non-identical models; the repository's existing layout note records this gap. [Layout research note](layout_methods.md)
- The reading-order relation work motivates partial orders but does not specify a complete cross-document schema for non-text figures, all table semantics, RTL/mixed-direction text, or cross-page continuation. [Zhang et al.](https://aclanthology.org/2024.emnlp-main.540/)
- Markdown, plain text and CSV cannot faithfully express every combination of table spans, nested structure, figure assets, coordinate geometry and ambiguous ordering. The exact projection contract must be stated for each exporter; Docling documents some of these format-specific losses. [Docling Serialization](https://docling-project.github.io/docling/concepts/serialization/)
- A universal meaning/calibration for a parser confidence score is not established. Docling says its numerical scores are informational/internal and that computation/weighting may change; its current confidence documentation lists `table_score` as not implemented. [Docling Confidence Scores](https://docling-project.github.io/docling/concepts/confidence_scores/)

## How should outputs be serialized and chunked for LLM consumption while retaining multimodal and layout-grounded evidence?

### Takeaway

Produce LLM-friendly representations from the canonical structure rather than making plain text the canonical parse. Chunk on semantic/document boundaries first and token limits second; repeat necessary context such as headings and table headers, and preserve links from every chunk back to its original elements, page coordinates and figure/table assets.

### Cited Findings

- Docling provides Markdown, HTML and DocTags serializers and documents serializer-specific behavior. Its serialization APIs can return metadata identifying document components contributing to the result; Markdown is convenient, but cell spans are flattened there while JSON/HTML preserve them. [Docling Serialization](https://docling-project.github.io/docling/concepts/serialization/)
- Docling defines chunking over `DoclingDocument` directly as an alternative to Markdown-then-text splitting. Its `HybridChunker` starts with hierarchical document chunks, splits only oversized chunks using a selected tokenizer, and can merge undersized successive chunks when headings/captions match; table headers can be repeated across table chunks. [Docling Chunking](https://docling-project.github.io/docling/concepts/chunking/)
- Docling's `HierarchicalChunker` makes element-level chunks and attaches relevant headers/captions. Its line-based chunker prioritizes keeping lines intact, useful for structured content such as tables, code and lists. [Docling Chunking](https://docling-project.github.io/docling/concepts/chunking/)
- Unstructured's basic chunking combines sequential typed elements up to soft/hard size limits, isolates tables, and splits only an oversized element; its title-based mode can preserve section boundaries. It cautions that metadata like page number/coordinates may not consolidate to one value, and exposes original constituent elements in chunk metadata so the source geometry can be recovered. [Unstructured chunking](https://docs.unstructured.io/open-source/core-functionality/chunking)
- MinerU emits multiple output targets, including Markdown, HTML, LaTeX, DOCX, PDF and structured-content formats; its saved result packages Markdown, middle JSON, structured content and image assets, with shared asset references. It documents that some entrypoints expose only subsets of all render targets. [MinerU output format and result contract](https://opendatalab.github.io/MinerU/reference/output_files/)
- Nougat is a vision-transformer OCR system designed to convert scientific-document page images into markup, motivated in part by semantic information lost when scientific content is represented as PDF. Its task and demonstrated domain are scholarly documents, not a general replacement for PDF text extraction or a universal document parser. [Nougat paper](https://arxiv.org/abs/2308.13418)
- Docling's report describes using the PDF text layer for text content and coordinates, page images for visual layout/table models, and re-aligning visual structure predictions to existing PDF text. Its example notes figure-body text may be omitted from Markdown while figure/caption relations survive in JSON. [Docling Technical Report](https://arxiv.org/html/2408.09869v5)
- The repository README describes current extraction grounding as deterministic matching against extracted text, with no extra LLM call; it also explicitly says the project is not a vision-LLM pipeline. Extending this to visual evidence would therefore be a separate capability rather than a claim about the current system. [Project README](../../README.md)

### Inferences

- Offer three complementary outputs from a single parsed document:
  1. **Canonical structured JSON** for round trips, audits and machine consumers, including geometry, hierarchy, relations, tables and asset references.
  2. **Readable Markdown** for lightweight prompts and inspection, with stable conventions for headings, lists, table rendering and explicit placeholders/links for figures rather than silently dropping them.
  3. **Evidence-aware chunks** for retrieval/LLM calls, containing text plus metadata (`document_id`, `element_ids`, page(s), bounding boxes, section path, relation context, source/provenance, and asset/table references).
- Chunk at semantic boundaries (section, paragraph, list, table row/group, caption/figure relation) and use the actual target tokenizer for the final limit. For oversized single elements, split with overlap only as a fallback; retain the original element IDs and part offsets so text can be traced back to source. This balances Docling's token-aware strategy and Unstructured's element-first strategy without adopting either API wholesale.
- Keep tables atomic when they fit. For oversized tables, split by rows or coherent row groups, include column headers in each chunk, and carry table ID, row/column indices, spans and source cell IDs. Avoid splitting a row if possible; if forced, record the split and preserve all cells. Use structured JSON/HTML as the fidelity path and Markdown as the LLM-friendly approximation.
- For figures, charts and image-only content, emit a text chunk containing caption/nearby context plus an asset/crop reference and bbox. Optional image captioning/OCR/VLM enrichment may add descriptions as attributed derived content, but should not overwrite the original figure or masquerade as source text. Any generated description must identify its method/model and remain distinguishable from extracted text.
- For extraction, use chunk metadata and evidence IDs to provide field-level page and region grounding. The extraction output can retain exact quoted text/coordinates and distinguish direct text support from inferred interpretation; the current text-string grounding mechanism remains a useful baseline for text-supported fields.
- Keep serialization, chunking and extraction separate APIs/stages. Different tasks need different views and token limits, and a document should not need to be reparsed merely because an embedding model or downstream serialization policy changes.
- For visual review, consider a debug export that overlays element boxes, table cells, source routes and confidence on rendered pages. This is an inference from geometry-rich model outputs and the repo's existing inspect command; validate usefulness with users before adding a broad UI surface.

### Gaps

- There is no universal best chunking strategy or token size established by the cited converter documentation. Optimal boundaries depend on retrieval task, tokenizer, embedding model, table question types and whether consumers can retrieve original elements.
- The cited sources document structural chunking and preserved metadata, but do not establish that any particular Markdown/table serialization improves extraction accuracy for fastdocparse's target LLMs. A task-specific evaluation should compare schema extraction, retrieval recall, prompt size and evidence recovery.
- Nougat's scholarly markup results do not establish robust general-purpose figure understanding, chart data extraction, OCR of arbitrary business forms, or coordinate-level field evidence. [Nougat paper](https://arxiv.org/abs/2308.13418)
- Current fastdocparse extraction grounding verifies values against extracted text, not directly against pixels, table-cell geometry or image regions. Extending grounding to OCR/visual evidence requires preserving OCR word boxes, region references and text-to-source mappings, then measuring false-grounded and missed-evidence rates. [Project README](../../README.md); [layout research note](layout_methods.md)
