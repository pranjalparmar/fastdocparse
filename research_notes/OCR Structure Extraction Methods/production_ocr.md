# Production OCR and Document Extraction Systems (as of Nov. 12, 2026)

## Which systems use modular OCR/layout/structure pipelines versus end-to-end multimodal models, and what do users actually receive?

### Takeaway

The market includes three distinguishable designs: OCR engines that expose recognized words and geometry, modular document-analysis pipelines that combine OCR with layout/table/form models, and document-specialized vision-language models (VLMs) that generate structured representations directly or through a small number of region-level stages. Cloud APIs commonly return a rich JSON evidence object; Markdown, HTML, searchable PDF, CSV, and other exports are renderings or downstream serializations, not proof that the recovered structure is correct.

### Cited Findings

- **Paradigm taxonomy.** OmniDocBench describes pipeline methods as decomposing parsing into layout analysis, OCR, formula/table recognition, and reading-order estimation; end-to-end VLMs produce structured representations such as Markdown directly. The paper cautions that fair comparison is difficult because benchmark coverage and metrics have been limited. — Linke Ouyang et al., “OmniDocBench: Benchmarking Diverse PDF Document Parsing with Comprehensive Annotations,” arXiv (Mar. 25, 2025), [paper](https://arxiv.org/html/2412.07626v2).
- **Google Document AI.** The conventional Document AI processor family returns `Document`/`Document.pages` structures with OCR text anchors, page anchors, bounding polygons, layout confidence, and layout objects; response handling is based on a protobuf/JSON representation. The Layout Parser is a hybrid: Google documents specialized OCR plus Gemini generative capabilities, a multi-stage parse/structure, annotate/verbalize, and chunk/augment process, and a `DocumentLayout` hierarchy. It can emit context-aware chunks as well as document structure; this is not merely raw OCR text. — Google Cloud, “Document AI Document resource (REST),” current API reference, [schema](https://docs.cloud.google.com/document-ai/docs/reference/rest/v1/Document); Google Cloud, “Process documents with Gemini layout parser,” current documentation (accessed Nov. 12, 2026), [guide](https://docs.cloud.google.com/document-ai/docs/layout-parse-chunk).
- **Microsoft Azure Document Intelligence.** Azure describes the Layout API as enhanced OCR plus deep-learning models. It supplies pages, paragraphs and roles, lines/words, selection marks, tables/cells and figures/sections in JSON. It can also return `content` in Markdown, with v4.0 representing tables as HTML inside the Markdown content. — Microsoft, “Document layout analysis – Document Intelligence – Foundry Tools,” updated May 1, 2026, [documentation](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0).
- **Amazon Textract.** Textract exposes explicit block graphs rather than a single Markdown artifact: PAGE, LINE, WORD, TABLE, CELL, KEY_VALUE_SET, QUERY_RESULT, geometry, confidence, and relationship IDs. Clients reconstruct downstream text, forms, tables, or markup by traversing those blocks. — Amazon Web Services, “Text Detection and Document Analysis Response Objects” and “Tables,” Amazon Textract Developer Guide (docs updated continuously; accessed Nov. 12, 2026), [response model](https://docs.aws.amazon.com/textract/latest/dg/how-it-works-document-layout.html), [tables](https://docs.aws.amazon.com/textract/latest/dg/how-it-works-tables.html).
- **ABBYY.** ABBYY has different products with different output contracts. FineReader PDF is an interactive OCR/PDF application with export to formats including searchable PDF, DOC(X), XLS(X), HTML, RTF, and TXT; FineReader Engine exposes JSON export via SDK. Vantage OCR Skill JSON separates physical `layout` from logical `content` and represents text, graphics, tables, lists, paragraphs, and estimated logical document structure. Vantage document-processing results can additionally contain schema-driven extracted fields and annotations. — ABBYY, “ABBYY FineReader PDF User’s Guide,” v16 (guide), [PDF](https://help.abbyy.com/assets/en-us/finereader/16/Users_Guide.pdf); ABBYY, “Data Extraction,” FineReader Engine documentation (current, accessed Nov. 12, 2026), [SDK example](https://docs.abbyy.com/fine-reader/engine/guided-tour/basic-usage-scenarios-implementation/data-extraction); ABBYY, “OCR Skill JSON Schema,” Vantage Developer documentation (current, accessed Nov. 12, 2026), [schema](https://docs.abbyy.com/vantage/developer/output/json/ocr/ocr-json-schema); ABBYY, “Understanding your results,” Vantage docs (current, accessed Nov. 12, 2026), [guide](https://docs.abbyy.com/vantage/getting-started/results).
- **PaddleOCR/PaddleOCR-VL.** These should not be conflated. The standard PP-OCR path is a modular detection → orientation correction → recognition pipeline. PP-StructureV3 layers preprocessing, OCR, layout analysis, element-specific table/formula/chart recognition and postprocessing/reading-order recovery. PaddleOCR-VL adds a compact VLM for document parsing, with the official pipeline combining layout detection and a VLM; its current PaddleX example saves JSON and Markdown, and can restructure multipage results and optionally merge cross-page tables. — Cheng Cui et al., “PaddleOCR 3.0 Technical Report,” arXiv (Jul. 7, 2025), [paper](https://arxiv.org/abs/2507.05595); PaddlePaddle, “Tutorial for PaddleOCR-VL Series Pipelines,” PaddleX documentation (current, accessed Nov. 12, 2026), [guide](https://paddlepaddle.github.io/PaddleX/latest/en/pipeline_usage/tutorials/ocr_pipelines/PaddleOCR-VL.html); PaddlePaddle, [PaddleOCR repository](https://github.com/PaddlePaddle/PaddleOCR).
- **Tesseract and EasyOCR.** Tesseract is an offline OCR engine, not a complete general-purpose document-structure parser: it exports text, hOCR, TSV, ALTO, PAGE XML and searchable PDF; hOCR/TSV carry word positions and confidence-like values. EasyOCR exposes detected quadrilateral boxes, text and recognition confidence; its documented API separates detection and recognition, but it does not itself promise semantic page layout, tables, reading order, or form understanding. — Tesseract OCR project, [repository and license](https://github.com/tesseract-ocr/tesseract), and [Command Line Usage](https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html) (current docs, accessed Nov. 12, 2026); JaidedAI, [EasyOCR repository and API](https://github.com/JaidedAI/EasyOCR) (current, accessed Nov. 12, 2026), [API documentation](https://www.jaided.ai/easyocr/documentation/).
- **IBM Docling and Granite-Docling illustrate a hybrid open ecosystem.** Classic Docling is a modular PDF/document-conversion pipeline built around specialized layout and table models, optional OCR, reading order and a unified document representation; it exports Markdown, HTML and lossless JSON. IBM’s Granite-Docling-258M is a document-specific VLM which emits DocTags, an intermediate representation that can then be converted to Markdown, JSON or HTML. — Deep Search Team, IBM Research, “Docling Technical Report,” arXiv (Aug. 2024), [paper](https://arxiv.org/abs/2408.09869); Docling project, [repository](https://github.com/docling-project/docling); IBM, “IBM Granite-Docling: End-to-end document understanding with one tiny model,” Sep. 24, 2025, [announcement](https://www.ibm.com/new/announcements/granite-docling-end-to-end-document-conversion).
- **Other specialist document parsers.** OmniDocBench characterizes MinerU and Marker as modular pipelines and specialized models such as Nougat/GOT-OCR as end-to-end expert models. These tools can yield Markdown/HTML/LaTeX but may not expose all word- and cell-level provenance in the same form as cloud OCR JSON. — Ouyang et al., “OmniDocBench,” arXiv (Mar. 25, 2025), [paper](https://arxiv.org/html/2412.07626v2).
- **Markdown is a serialization, not validation.** Microsoft’s Markdown response uses embedded HTML tables specifically for merged/multirow headers; ABBYY, PaddleX, Docling and Google provide structured data or intermediate schemas from which text can be serialized. Markdown syntax has no native representation for many geometry, confidence, merged-cell, source-page, or relation fields. So “Markdown output” establishes an output encoding, not reliable reading order, exact cell topology, or a preserved link to source evidence. This last sentence is a cross-source inference, not a vendor claim. — Microsoft, “Document layout analysis” (May 1, 2026), [documentation](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0); ABBYY, “OCR Skill JSON Schema,” [schema](https://docs.abbyy.com/vantage/developer/output/json/ocr/ocr-json-schema); PaddlePaddle, “PaddleOCR-VL Series Pipelines,” [guide](https://paddlepaddle.github.io/PaddleX/latest/en/pipeline_usage/tutorials/ocr_pipelines/PaddleOCR-VL.html).

### Inferences

- Products called “OCR” vary substantially in scope. Word recognition, region/layout classification, reading-order inference, table topology, schema extraction, and rendering are distinct capabilities and may be separate models or API features.
- A JSON response is generally the more informative inspection/provenance artifact; a Markdown export is useful for reading and retrieval but usually loses structure/evidence fields unless the source schema or a parallel JSON is retained.
- “End-to-end” should be read as task/model interface, not necessarily one monolithic neural network: current commercial and open examples often combine VLMs with layout models, document preprocessing, or a canonical intermediate representation.

### Gaps

- Public documentation does not disclose the full internals or per-stage model boundaries of several managed services (ABBYY Vantage, Document AI, Azure, Textract); the table above classifies only the publicly described architecture and output behavior.
- FineReader PDF export details vary by edition, OS, and export setting. Treat the cited guide as an illustrative supported-format list rather than a promise that every product SKU exports every format.

## How are tables, merged cells, columns, figures, handwriting, reading order, and confidence represented?

### Takeaway

The most inspectable output tends to preserve elements, geometry, and relationships (e.g., Azure cells with row/column spans, Textract block relationships, ABBYY layout/content objects, or Google text/page anchors). In contrast, a plain text/Markdown-only result can conceal whether the system truly identified a merged cell, figure region, evidence location, or uncertain recognition; cross-page tables and dense/multicolumn layouts remain recurring hard cases.

### Cited Findings

- **Tables, cells and merged structure.** Textract returns TABLE and CELL blocks with `RowIndex`, `ColumnIndex`, `RowSpan`, `ColumnSpan`, geometry, confidence, child WORD blocks and `MERGED_CELL` relationships. It also labels header cells, table title/footer, structured versus semistructured tables, and summary cells. — AWS, “Tables – Amazon Textract,” Developer Guide (current, accessed Nov. 12, 2026), [documentation](https://docs.aws.amazon.com/textract/latest/dg/how-it-works-tables.html).
- **Azure tables.** Azure Layout returns row/column counts and per-cell row/column indices, spans, content and bounding polygons, and identifies `columnHeader`; rotated tables are supported. Azure documentation explicitly advises that tables spanning pages may need splitting and post-processing to reunite them. The v4 Markdown serialization represents tables as HTML, allowing merged cells and multirow headers to be expressed. — Microsoft, “Document layout analysis” (May 1, 2026), [documentation](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0).
- **Google table representation.** The Document AI API schema defines layout/table rows and page anchors, while Layout Parser advertises advanced parsing of merged/intricate table headers and contextual chunking. Its own guide documents a limitation: PDF tables spanning multiple pages might be split into two tables. The claim that it “excels” is Google’s product claim, not independent evidence. — Google Cloud, “Document resource (REST),” [API schema](https://docs.cloud.google.com/document-ai/docs/reference/rest/v1/Document); Google Cloud, “Process documents with Gemini layout parser,” current guide, [capabilities and limitations](https://docs.cloud.google.com/document-ai/docs/layout-parse-chunk).
- **ABBYY Vantage.** Its OCR Skill JSON has separate physical layout and logical content objects; the documented schema covers graphics, text, tables, lists, paragraphs, paragraph functions, and logical sections. Its separate structured extraction result represents named fields, values, confidence annotations and human-verification flags. — ABBYY, “OCR Skill JSON Schema,” Vantage documentation (current, accessed Nov. 12, 2026), [schema](https://docs.abbyy.com/vantage/developer/output/json/ocr/ocr-json-schema); ABBYY, “Understanding your results,” [result structure](https://docs.abbyy.com/vantage/getting-started/results).
- **Columns and reading order.** Azure returns text/layout roles and hierarchical sections, but ordering and interpretation still require using those fields. PaddleOCR PP-StructureV3 explicitly has reading-order recovery; PaddleOCR-VL’s examples include multipage restructuring and optional table merging. Docling returns layout/reading order in its document representation and suppresses headers/footers in a Markdown rendering in the technical report. — Cui et al., “PaddleOCR 3.0 Technical Report” (2025), [paper](https://arxiv.org/abs/2507.05595); PaddlePaddle, “PaddleOCR-VL Series Pipelines,” [guide](https://paddlepaddle.github.io/PaddleX/latest/en/pipeline_usage/tutorials/ocr_pipelines/PaddleOCR-VL.html); Staar et al., “Docling Technical Report,” [paper](https://arxiv.org/abs/2408.09869).
- **Figures and visual content.** Azure Layout can identify figure regions, polygons, related text spans/elements, captions, and optionally return cropped figure images. Google’s Gemini Layout Parser can add descriptive annotations for figures/charts; such verbalization is a generated interpretation and should be distinguished from OCR transcription. — Microsoft, “Document layout analysis” (May 1, 2026), [figures](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0); Google Cloud, “Process documents with Gemini layout parser,” [guide](https://docs.cloud.google.com/document-ai/docs/layout-parse-chunk).
- **Handwriting.** Azure’s Layout response includes handwritten-style classification with confidence over supported language/style spans; its word-level OCR still has confidence and geometry. Textract recognizes printed and handwritten text in English, including mixed printed/handwritten documents, and identifies `TextType`. Google Enterprise Document OCR supports handwriting hints and advertises handwriting-language support. PaddleOCR-VL’s paper reports handwriting among evaluated/demonstrated content types, but per-field calibrated confidence/evidence handling is not established by the paper’s Markdown examples. — Microsoft, “Document layout analysis” (May 1, 2026), [documentation](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0); AWS, “Amazon Textract recognizes handwriting and adds five new languages,” AWS Machine Learning Blog (Nov. 2020), [announcement](https://aws.amazon.com/blogs/machine-learning/amazon-textract-recognizes-handwriting-and-adds-five-new-languages/); Google Cloud, “Enterprise Document OCR,” current docs, [guide](https://docs.cloud.google.com/document-ai/docs/enterprise-document-ocr); Cui et al., “PaddleOCR-VL,” arXiv (2025), [paper](https://arxiv.org/abs/2510.14528).
- **Confidence is local evidence, not a correctness guarantee.** Textract attaches confidence percentages to blocks, including words and tables; Azure returns confidence at word, handwritten-style and selection-mark levels. Document AI defines confidence on layout and OCR results. ABBYY Vantage gives extracted field confidence, raw value/source, and `NeedVerification`/verification state. EasyOCR returns recognition confidence. Scores across these products are not demonstrated to be calibrated comparably. — AWS, “Text Detection and Document Analysis Response Objects,” [guide](https://docs.aws.amazon.com/textract/latest/dg/how-it-works-document-layout.html); Microsoft, “Document layout analysis” (May 1, 2026), [guide](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0); Google Cloud, “Document resource (REST),” [schema](https://docs.cloud.google.com/document-ai/docs/reference/rest/v1/Document); ABBYY, “Understanding your results,” [guide](https://docs.abbyy.com/vantage/getting-started/results); JaidedAI, [EasyOCR API documentation](https://www.jaided.ai/easyocr/documentation/).
- **Lightweight OCR formats.** Tesseract’s hOCR output nests page/area/paragraph/line/word elements with `bbox` and word `x_wconf`; TSV likewise exposes hierarchy, word text, coordinates and confidence. EasyOCR returns each detected text item as a quadrilateral plus text and score. Neither format inherently conveys semantic form-field association or full table cell topology. — Tesseract OCR project, “Command Line Usage,” current docs, [hOCR/TSV examples](https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html); JaidedAI, [EasyOCR repository](https://github.com/JaidedAI/EasyOCR).
- **Table and reading-order failures are measurable.** OmniDocBench’s authors identify difficult handwritten notes, newspapers, and dense layouts; they found reading-order accuracy dropped on multi-column/complex layouts and VLMs had difficulty on dense newspapers due to input-resolution and token-length limits. Their dataset includes merged-cell and rotated/table special cases. — Ouyang et al., “OmniDocBench” (Mar. 25, 2025), [paper](https://arxiv.org/html/2412.07626v2).
- **Evidence in canonical representations.** Docling’s original technical report notes that Markdown repeats a spanning header across columns, while JSON preserves table-cell span information; this illustrates a serialization tradeoff: the Markdown can be more convenient but alter/expose less of source topology. The report also notes that figure image text was dropped in its illustrated example although the figure caption was linked in JSON. — Deep Search Team, IBM Research, “Docling Technical Report,” arXiv (Aug. 2024), [paper](https://arxiv.org/abs/2408.09869).

### Inferences

- For auditability, preserve raw page images/PDF, parser version, page dimensions, JSON/protobuf, geometric coordinates, text anchors/spans, confidence, and relationships. Derive Markdown/HTML afterward and keep stable references to the underlying elements.
- Word-level confidence and box geometry are helpful for targeted review but do not ensure correct semantic grouping; a high-confidence OCR word can still be assigned to the wrong column, row, field, or figure caption.
- Tables are better handled by comparing cell topology plus content, not only extracted flattened text. HTML is more expressive than Markdown tables for `rowspan`/`colspan`, but still may not retain exact source polygon, detection confidence, or visual evidence unless paired with structured JSON.
- Cross-page table assembly, figure/chart interpretation, and unconstrained reading order are separate tasks. A parser’s support for single-page cells or headings should not be read as a guarantee of semantic cross-page joins or chart understanding.

### Gaps

- The public APIs do not offer a uniform definition or calibration protocol for their confidence values; no cross-vendor conversion of (say) 0.9 to a shared error probability is supported by the cited evidence.
- Product documentation describes supported elements but usually does not specify error rates for merged cells, handwritten values, charts, or mixed-column reading order on a common test set.
- VLM documentation often reports generated figure descriptions without a claim that the description is strictly extractive or supported by element-level source citations. Validate visually important figures against the page image.

## What is available open-source, hosted, enterprise/offline, what are documented constraints/costs, and what benchmark gaps remain?

### Takeaway

Tesseract, EasyOCR, PaddleOCR/PaddleOCR-VL, and Docling are locally deployable/open-source alternatives (subject to each model/code license); Azure, Google Document AI, Textract, and ABBYY Vantage are commercial managed services, with some Azure/ABBYY enterprise deployment options. Costs and request ceilings are feature-specific, and public benchmark scores are not a substitute for a matched evaluation on the intended documents; public evidence contradicts “perfect structure” claims, especially on multi-column reading order, cross-page tables, merged cells, handwriting, noisy scans and dense pages.

### Cited Findings

- **Tesseract.** Apache-2.0 OCR engine; runs locally/offline and provides no per-page service charge. It takes image input in its standard CLI (PDF workflows typically need a wrapper/rasterizer); it is not a document layout/form/table API. Tesseract emits hOCR, TSV, ALTO, PAGE, and searchable PDF. — Tesseract OCR project, [repository/license](https://github.com/tesseract-ocr/tesseract) and [CLI docs](https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html), current/accessed Nov. 12, 2026. (The PDF-input caveat is also documented by OCRmyPDF’s explanation of the PDF wrapper workflow: [OCRmyPDF cookbook](https://ocrmypdf.readthedocs.io/en/latest/introduction.html), accessed Nov. 12, 2026.)
- **EasyOCR.** Apache-2.0, local Python library, downloadable models, 80+ languages; detects text regions and recognizes text with quadrilaterals/text/confidence. No charge per API page, but users provision and operate the runtime; repository is a recognizer, not a full PDF page-layout/form parser. — JaidedAI, [EasyOCR repository](https://github.com/JaidedAI/EasyOCR) and [API docs](https://www.jaided.ai/easyocr/documentation/), current/accessed Nov. 12, 2026.
- **PaddleOCR.** Open-source Apache-licensed toolkit with PP-OCRv5, PP-StructureV3 and PP-ChatOCRv4 per its technical report. PaddleOCR-VL has downloadable model weights and documented local pipeline/JSON/Markdown output; repositories and dependencies expose self-hosted deployment. Separately, PaddleOCR’s optional hosted/AI Studio service is not the same thing as locally running open-source weights. Exact available license can differ by individual model/asset, so check model cards and dependency licenses. — Cui et al., “PaddleOCR 3.0 Technical Report,” arXiv (Jul. 7, 2025), [paper](https://arxiv.org/abs/2507.05595); PaddlePaddle, [PaddleOCR repository](https://github.com/PaddlePaddle/PaddleOCR); PaddleX, [PaddleOCR-VL pipeline guide](https://paddlepaddle.github.io/PaddleX/latest/en/pipeline_usage/tutorials/ocr_pipelines/PaddleOCR-VL.html).
- **Docling.** MIT-licensed, local/self-hostable document converter, supports optional OCR for scanned PDFs and Markdown/HTML/JSON export. Its classic path uses specialist layout/table/OCR components; Granite-Docling VLM is another option. A paper reports the model architecture and open-source status, but compute speed and memory depend on enabled models, hardware, OCR, and document composition. — Deep Search Team, IBM Research, “Docling Technical Report,” arXiv (Aug. 2024), [paper](https://arxiv.org/abs/2408.09869); Docling project, [repository](https://github.com/docling-project/docling); IBM, “Granite-Docling,” Sep. 24, 2025, [announcement](https://www.ibm.com/new/announcements/granite-docling-end-to-end-document-conversion).
- **Google Document AI pricing and page limits.** Pricing is per processor. Google’s public pricing table lists Layout Parser (including initial chunking) at $10 per 1,000 pages in the listed tier; pricing can depend on processor/region/volume. Current limits list Layout Parser at 15 pages synchronously and 500 pages per PDF asynchronously/batch. Layout Parser online input maximum is 20 MB; batch PDF maximum is 1 GB. — Google Cloud, “Document AI pricing,” current pricing (accessed Nov. 12, 2026), [pricing](https://cloud.google.com/products/document-ai/pricing); Google Cloud, “Limits,” current limits, [page caps](https://docs.cloud.google.com/document-ai/limits); Google Cloud, “Process documents with Gemini layout parser,” [file limits](https://docs.cloud.google.com/document-ai/docs/layout-parse-chunk).
- **Azure Document Intelligence constraints and deployment.** Current Layout docs say paid S0 processes PDFs/TIFFs up to 2,000 pages and files up to 500 MB; F0 processes only the first two pages and accepts files to 4 MB. It supports figures/tables/Markdown; API quota details vary by model and region. Standard hosted service pricing begins at $1.50 per 1,000 pages for Read (not the same as all layout/extraction processing). Microsoft also documents connected and disconnected containers, which require commitment-based pricing/licensing; disconnected deployment is not a free offline substitute. — Microsoft, “Document layout analysis” (May 1, 2026), [constraints](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0); Microsoft, “Azure Document Intelligence in Foundry Tools pricing,” current, [pricing](https://azure.microsoft.com/en-us/pricing/details/document-intelligence/); Microsoft, “Use Document Intelligence containers in disconnected environments,” current, [offline deployment](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/containers/disconnected?view=doc-intel-4.0.0).
- **Amazon Textract costs.** AWS pricing separates operations/features: Detect Document Text is $1.50 per 1,000 pages for the first million pages/month in the listed region; tables $15/1,000, forms $50/1,000, queries $15/1,000, and feature combinations stack; Layout alone is listed at $4/1,000 (region, tier, and request type matter). Textract is a hosted AWS service rather than a downloadable on-prem engine. — Amazon Web Services, “Amazon Textract pricing,” current pricing (accessed Nov. 12, 2026), [pricing](https://aws.amazon.com/textract/pricing/).
- **ABBYY deployment and pricing.** FineReader PDF is a licensed desktop product; FineReader Engine is an SDK. Vantage is a commercial enterprise IDP offering with cloud and on-premises/private-cloud deployment options and quote/contract-based pricing rather than a transparent public per-page list. Its output schemas can preserve layout/content and field confidence but availability of skill/model and deployment depends on product edition/license. — ABBYY, “ABBYY FineReader PDF User’s Guide,” v16, [guide](https://help.abbyy.com/assets/en-us/finereader/16/Users_Guide.pdf); ABBYY, “ABBYY Vantage,” current product page (accessed Nov. 12, 2026), [deployment FAQ](https://www.abbyy.com/vantage/); ABBYY, “OCR & Document Processing API,” current, [product/API](https://www.abbyy.com/ai-document-processing/api/).
- **What benchmark scores can and cannot establish.** OmniDocBench v1 includes 981 PDF pages from nine document types, with diverse layout, OCR, table and formula annotations. Its authors report (a) multi-column/complex layouts lower reading-order scores across methods, (b) dense newspapers challenge VLMs due to resolution/token limits, (c) some general VLMs generalize better to notes/degraded input, while specialized pipelines perform well on standard papers/reports. The paper’s initial results do not evaluate every current commercial API/version, so they cannot rank the full vendor field in 2026. — Linke Ouyang et al., “OmniDocBench,” arXiv v2 (Mar. 25, 2025), [paper](https://arxiv.org/html/2412.07626v2), [dataset/code](https://github.com/opendatalab/OmniDocBench).
- **Benchmarks are task- and dataset-specific.** OmniDocBench discusses limitations in narrow document-type coverage and generic string metrics for tables/formulas, so it introduces end-to-end, task-specific and attribute-based evaluation. Later comparisons must match exact model/API version, preprocessing, pages, languages, and output settings. A 2026 ACL Industry paper, “When Good OCR Is Not Enough: Benchmarking OCR Robustness for Retrieval-Augmented Generation,” argues that standard OCR metrics can miss structurally consequential loss such as table and reading-order errors, and presents industrial document challenges including cross-page tables and extreme layouts. — Ouyang et al., “OmniDocBench,” [paper](https://arxiv.org/html/2412.07626v2); authors, “When Good OCR Is Not Enough: Benchmarking OCR Robustness for Retrieval-Augmented Generation,” ACL Anthology (2026), [paper](https://aclanthology.org/2026.acl-industry.60.pdf).
- **No evidence supports a universal winner or perfect output.** The systems expose different output formats and features, and existing benchmark comparisons often use different inputs, API versions, prompts, preprocessing, and metrics. OmniDocBench reports non-zero error on evaluated methods and clear category-specific weaknesses; the source literature explicitly states that a common comprehensive benchmark has been lacking. — Ouyang et al., “OmniDocBench” (Mar. 25, 2025), [paper](https://arxiv.org/html/2412.07626v2).

### Inferences

- For privacy-sensitive/offline work, evaluate local Tesseract/EasyOCR/PaddleOCR/Docling and self-hosted VLM models; operational cost shifts from per-page fees to GPU/CPU, storage, model maintenance, licensing review, and human quality control.
- For managed-service planning, calculate using the exact requested feature (OCR vs layout vs forms/tables vs document-specific extraction), region, volume tier, synchronous/batch mode, and any model hosting charges. Do not compare a $1.50 basic OCR price to a layout/form parser as if their outputs were equivalent.
- Stronger comparison protocol: select a representative, legally usable, held-out sample; keep source PDFs/scans; evaluate transcript fidelity (CER/WER or normalized edit), region detection (IoU/mAP), table content and topology (cell/row/column/span metrics such as TEDS plus semantic checks), reading order, form-field correctness, and figure/chart handling; record per-category results, latency, price, model/version, failures, and confidence calibration.
- Treat product-specific numbers and output formats as snapshots. API versions and managed model aliases can change, so freeze explicit versions in reproducibility records and re-run the exact evaluation on upgrades.

### Gaps

- There is no documented apples-to-apples public benchmark in the cited material that compares current ABBYY Vantage, current Document AI/Layout Parser versions, current Azure v4, Textract, Tesseract, EasyOCR, PaddleOCR-VL, and Docling against the same PDFs/scans, with same output requirements and same metrics.
- Public list prices can vary by cloud region, committed volume, processor/model, enterprise contract, container SKU, add-ons, and billing unit. ABBYY Vantage pricing is not transparent in a public per-page schedule; query exact quotes rather than inferring cost.
- “Offline” requires nuance: an engine can run locally while weights, OCR models, optional VLMs, licensing activation, telemetry, or dependencies may require prior downloads or network access. Verify each model’s license, runtime, and air-gap procedure separately.
- Open weights/code are not identical to unrestricted commercial use; model-card and dependency terms may diverge from the repository’s primary code license. Verify before deploying.
