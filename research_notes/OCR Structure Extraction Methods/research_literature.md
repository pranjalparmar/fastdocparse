# Document OCR, Layout, Reading Order, and Structured Conversion

**Research cutoff: 12 November 2026.** This note distinguishes recognition (what marks/text are present), geometric layout analysis (where regions are and their visual class), logical structure and reading order (how regions relate and are traversed), table structure recognition (cells, spans, headers and contents), semantic extraction (task-specific values/relations), and serialization (a choice of Markdown/HTML/JSON representation). They are related pipeline stages, not synonyms, and a score on one does not establish correctness on the others.

## What technical families solve the component tasks, and what are their tradeoffs?

### Takeaway

The literature supports a spectrum from explicit, modular document analysis to image-to-markup generation. Traditional OCR and native-PDF extraction are strong at recovering text with coordinates when their input assumptions hold; visual layout/table experts add explicit structure; multimodal pretraining supports semantic tasks; autoregressive image-to-markup systems jointly predict several stages but can obscure error provenance and hallucinate or omit content. Reading order and table grids remain independent inference problems, while Markdown is a lossy serialization target rather than the underlying document structure.

### Cited Findings

- **Classic OCR/document-analysis pipeline.** A conventional OCR system detects/segments text, recognizes characters or words, and emits text plus locations; layout analysis first separates page regions and/or text lines and imposes an order. Tesseract's architecture paper describes a stepwise engine including connected-component analysis, line finding, word recognition, and adaptive classification; it does not claim to infer a complete semantic document tree. — Ray Smith, “An Overview of the Tesseract OCR Engine,” ICDAR 2007, [DOI 10.1109/ICDAR.2007.4376991](https://doi.org/10.1109/ICDAR.2007.4376991); [author-hosted paper](https://tesseract-ocr.github.io/docs/tesseracticdar2007.pdf).
- **Rule-based / geometric layout analysis.** Recursive XY-cut, whitespace/projection methods and bottom-up connected-component or Docstrum-style methods exploit whitespace, alignment, and region geometry to segment pages and derive an order. They are fast and interpretable when page geometry matches assumptions, but heuristic cuts can break irregular/non-Manhattan layouts, nested regions, overlapping columns, or mixed orientations. — Jean-Luc Meunier, “Optimized XY-Cut for Determining a Page Reading Order,” ICDAR 2005, [paper](https://static.aminer.org/pdf/PDF/000/295/221/optimized_xy_cut_for_determining_a_page_reading_order.pdf); O’Gorman, “The Document Spectrum for Page Layout Analysis,” *IEEE TPAMI* 15(11), 1993, [DOI 10.1109/34.244676](https://doi.org/10.1109/34.244676).
- **Digital-born PDF extraction is not image OCR.** A PDF is a rendering format whose operators, glyphs and positioned characters do not necessarily encode paragraph, section, or semantic reading order. Text extraction from positioned PDF glyphs needs grouping and ordering; image OCR is needed for raster-only content, not for native text already available. A large benchmark derived from parallel TeX/PDF demonstrates extraction is measurable but not fully solved. — Hannah Bast and Claudius Korzen, “A Benchmark and Evaluation for Text Extraction from PDF,” JCDL 2017, [DOI 10.1109/JCDL.2017.7991564](https://doi.org/10.1109/JCDL.2017.7991564); [paper](https://ad-publications.cs.uni-freiburg.de/benchmark.pdf).
- **Layout detection plus OCR.** A modular pipeline detects page elements (e.g. title, paragraph, table, figure), intersects boxes with native PDF words or OCR tokens, groups tokens into elements, orders the elements, then delegates table/figure subproblems. The modularity makes stages inspectable and selectively replaceable, but errors propagate: missed region → missing text; bad box/token assignment → wrong element; ordering or segmentation error → scrambled serialization. Docling reports this architecture explicitly: PDF backends, page layout detector, OCR where needed, specialized TableFormer, and post-processing into a typed `DoclingDocument`, exported to Markdown/JSON. Its technical report says JSON serialization is lossless for its representation while Markdown/HTML export is lossy. — Christoph Auer et al., “Docling Technical Report,” arXiv:2408.09869 (2024; v5 Dec. 2024), [arXiv](https://arxiv.org/abs/2408.09869); [HTML full text](https://arxiv.org/html/2408.09869v3).
- **LayoutLM family: text/layout/vision representations, not a generic PDF-to-Markdown transcriber.** LayoutLM jointly encodes OCR text and 2-D boxes, later variants add visual features and improved multimodal objectives. The original paper evaluates downstream form/receipt entity labeling and document classification; it takes OCR tokens/layout as input, and its sequence-labeling outputs are task-specific entities, not a complete layout tree or arbitrary markup. LayoutLMv2/v3 and multilingual LayoutXLM extend multimodal pretraining. LayoutLMv3 uses unified text/image masking and word-patch alignment and evaluates form, receipt, document VQA, classification and layout-analysis tasks. — Yiheng Xu et al., “LayoutLM: Pre-training of Text and Layout for Document Image Understanding,” KDD 2020, [DOI 10.1145/3394486.3403172](https://doi.org/10.1145/3394486.3403172), [arXiv](https://arxiv.org/abs/1912.13318); Yupan Huang et al., “LayoutLMv3,” ACM MM 2022, [arXiv:2204.08387](https://arxiv.org/abs/2204.08387), [Microsoft Research](https://www.microsoft.com/en-us/research/publication/layoutlmv3-pre-training-for-document-ai-with-unified-text-and-image-masking/).
- **DocFormer** is another multimodal encoder using text, image and spatial features, pretrained for cross-modal interaction and evaluated on visual document understanding benchmarks. It is useful evidence for multimodal representation learning, not a whole-page structural serializer: its defined downstream tasks include entity grouping/sequence labeling and classification. — Srikar Appalaraju et al., “DocFormer: End-to-End Transformer for Document Understanding,” ICCV 2021, pp. 993–1003, [DOI 10.1109/ICCV48922.2021.00103](https://doi.org/10.1109/ICCV48922.2021.00103), [arXiv:2106.11539](https://arxiv.org/abs/2106.11539).
- **Reading order as sequence prediction.** LayoutReader learns a sequence-to-sequence permutation over OCR words using text and layout, trained/evaluated with ReadingBank. ReadingBank has 500,000 pages, with reading-order labels weakly derived from Word XML; this is scale-efficient, but Word-authored layouts and their embedded order are not a universal account of reading on every scanned or visually ambiguous page. — Zijun Wang et al., “LayoutReader: Pre-training of Text and Layout for Reading Order Detection,” EMNLP 2021, [ACL Anthology](https://aclanthology.org/2021.emnlp-main.389/); [ReadingBank repository](https://github.com/doc-analysis/ReadingBank).
- **Reading order as graph/relations.** A single permutation over all regions may overstate the truth: some regions are independent or multiple traversal orders are acceptable. Zhang et al. model immediate succession as relations in a directed acyclic graph and introduce relation annotations/baselines; their paper reports sequence-based methods can be limited by incomplete supervision. Layout2Pos instead predicts layout-aware position embeddings and shows robustness concerns when evaluation ordering differs from training ordering. These approaches are more expressive than a total order but require relation/group-level ground truth and still need a policy for serialization. — Chong Zhang et al., “Modeling Layout Reading Order as Ordering Relations for Visually-rich Document Understanding,” EMNLP 2024, [ACL Anthology](https://aclanthology.org/2024.emnlp-main.540/), [arXiv:2409.19672](https://arxiv.org/abs/2409.19672); Laura Nguyen et al., “Learning Reading Order via Document Layout with Layout2Pos,” TPDL 2024, [Springer](https://link.springer.com/chapter/10.1007/978-3-031-72437-4_1).
- **Table detection and table structure are separate.** PubTables-1M supplies almost one million scientific-paper tables with detection, cell/layout, header and functional annotations. It explicitly addresses inconsistent over-segmentation by canonicalizing tables. Table Transformer (TATR) trains DETR-style models for table detection and for row/column/cell structure (and functional analysis); it does not make table identification equivalent to recovering a logically correct cell grid or reading cell text. — Brandon Smock, Rohith Pesala, and Robin Abraham, “PubTables-1M: Towards Comprehensive Table Extraction From Unstructured Documents,” CVPR 2022, pp. 4634–4642, [CVF](https://openaccess.thecvf.com/content/CVPR2022/html/Smock_PubTables-1M_Towards_Comprehensive_Table_Extraction_From_Unstructured_Documents_CVPR_2022_paper.html); [official TATR repository](https://github.com/microsoft/table-transformer).
- **Table structure models.** TableFormer predicts a sequence of structure tokens and cell boxes; for programmatically generated PDFs it can align predicted structure to native PDF text to avoid re-recognizing table content. On PubTabNet it reports improvements in TEDS over its baseline, including separate results for simple and complex tables. GriTS compares table matrices and splits topology, content, and location, giving more diagnostic measures than one text string score. These are table-specific structure/content metrics; none by itself assures correct table detection, cell meaning, cross-page linkage, or downstream numeric extraction. — Ahmed Nassar et al., “TableFormer: Table Structure Understanding With Transformers,” CVPR 2022, pp. 4614–4623, [CVF](https://openaccess.thecvf.com/content/CVPR2022/html/Nassar_TableFormer_Table_Structure_Understanding_With_Transformers_CVPR_2022_paper.html); Brandon Smock et al., “GriTS: Grid Table Similarity Metric for Table Structure Recognition,” arXiv:2203.12555 (2022), [arXiv](https://arxiv.org/abs/2203.12555).
- **Image-to-markup encoder-decoder.** Donut maps document images directly to task-shaped structured tokens without external OCR, avoiding a separate OCR dependency and its error propagation. It demonstrates visual document classification and information extraction/document parsing on selected datasets; it does not emit calibrated text boxes by default, and an output schema learned from task data is not necessarily a general-purpose, lossless document representation. — Geewook Kim et al., “OCR-Free Document Understanding Transformer,” ECCV 2022, pp. 498–517, [Springer](https://link.springer.com/chapter/10.1007/978-3-031-19815-1_29), [arXiv:2111.15664](https://arxiv.org/abs/2111.15664), [official repository](https://github.com/clovaai/donut).
- **Domain-specialized page-to-markup:** Nougat is a visual transformer trained to convert academic documents into markup with scientific math/table content; its intended domain is academic papers (not arbitrary business PDFs), and the official repository notes it works best with English papers and was trained on arXiv/PMC-like scientific papers. It is a recognizer/markup generator, not proof of general-purpose semantic parsing. — Lukas Blecher et al., “Nougat: Neural Optical Understanding for Academic Documents,” ICLR 2024, [ICLR proceedings](https://proceedings.iclr.cc/paper_files/paper/2024/hash/a39a9aceda771cded859ae7560530e09-Abstract-Conference.html), [arXiv:2308.13418](https://arxiv.org/abs/2308.13418), [official repository](https://github.com/facebookresearch/nougat).
- **Recent specialized VLM parsing and two-stage compromise.** olmOCR uses a fine-tuned 7B vision-language model for scalable PDF-to-linearized-text/Markdown-like extraction, preserving selected structure such as sections, tables and equations; olmOCR-bench evaluates text presence/absence, order, table and math properties with unit tests. Dolphin (ACL 2025) adopts “analyze then parse”: first generate layout elements in reading order, then parse heterogeneous elements with specialized prompts in parallel. This separates element discovery from element transcription but is still learned inference and model-specific, not a guarantee. — Jake Poznanski et al., “olmOCR: Unlocking Trillions of Tokens in PDFs with Vision Language Models,” arXiv:2502.18443 (2025), [arXiv](https://arxiv.org/abs/2502.18443), [official repository](https://github.com/allenai/olmocr); Jake Poznanski, Luca Soldaini, and Kyle Lo, “olmOCR 2: Unit Test Rewards for Document OCR,” arXiv:2510.19817 (2025), [arXiv](https://arxiv.org/abs/2510.19817); Hao Feng et al., “Dolphin: Document Image Parsing via Heterogeneous Anchor Prompting,” Findings of ACL 2025, [ACL Anthology](https://aclanthology.org/2025.findings-acl.1130/), [arXiv:2505.14059](https://arxiv.org/abs/2505.14059).
- **General multimodal LLMs/VLMs** can answer questions or generate a requested representation from visual context, enabling flexible extraction without a fixed task head. But answer correctness and document transcription/structure correctness differ: VQA may return one requested fact while silently omitting all other content; unconstrained generation may normalize, infer, or hallucinate. OCRBench v2 finds model limitations in fine-grained text, layout perception, complex-element parsing and reasoning despite broad multimodal capability. — Ling Fu et al., “OCRBench v2: An Improved Benchmark for Evaluating Large Multimodal Models on Visual Text Localization and Reasoning,” NeurIPS 2025 Datasets and Benchmarks Track, [proceedings](https://proceedings.neurips.cc/paper_files/paper/2025/hash/8c2e6bb15be1894b8fb4e0f9bcad1739-Abstract-Datasets_and_Benchmarks_Track.html), [arXiv:2501.00321](https://arxiv.org/abs/2501.00321).
- **Markdown/JSON conversion is a representation decision after inference.** A parser must decide whether to suppress repeating headers/footers, how to represent merged cells, lists, captions, formulas, footnotes, coordinates and multi-column flow. Markdown has no native representation for all visual/semantic relations; equivalent content can be encoded as pipe tables, HTML, or JSON with different fidelity and downstream behavior. Docling explicitly distinguishes its rich typed object and lossless JSON serialization from lossy Markdown/HTML export. — Auer et al., [Docling Technical Report](https://arxiv.org/html/2408.09869v3); Ouyang et al., [OmniDocBench paper](https://openaccess.thecvf.com/content/CVPR2025/html/Ouyang_OmniDocBench_Benchmarking_Diverse_PDF_Document_Parsing_with_Comprehensive_Annotations_CVPR_2025_paper.html).
- **Why generic “perfect structure” is not a realistic guarantee (inference grounded in the above):** (1) a visual page can admit more than one reasonable segmentation or reading traversal (e.g. footnote placement, sidebars, parallel columns); (2) PDF glyph order and semantic hierarchy can be absent or inconsistent; (3) document image quality and languages vary; (4) table structure can be underdetermined when borders are missing or merged cells are visually implied; (5) stages have independent errors and serialization necessarily discards information; (6) definitions of “correct” vary by downstream purpose. Relation-based reading order work explicitly notes a single total sequence can be incomplete, while PDF extraction and benchmark work document layout/ground-truth difficulties. Therefore quality should be specified by task, input type, tolerance, provenance, confidence and abstention behavior—not a universal perfection claim. — [Zhang et al., EMNLP 2024](https://aclanthology.org/2024.emnlp-main.540/); [Bast & Korzen, JCDL 2017](https://doi.org/10.1109/JCDL.2017.7991564); [Ouyang et al., CVPR 2025](https://openaccess.thecvf.com/content/CVPR2025/html/Ouyang_OmniDocBench_Benchmarking_Diverse_PDF_Document_Parsing_with_Comprehensive_Annotations_CVPR_2025_paper.html).

### Inferences

- OCR’s output should be treated as positioned observations, not already-correct paragraphs or reading order. The logical structure layer should preserve both raw tokens/boxes and derived groupings so that downstream corrections do not erase evidence.
- For a library whose goal is fast parsing rather than a single vertical task, native PDF text is the preferred source when trustworthy; OCR is a fallback for raster-only/failed text, not an obligatory repeated pass over text already encoded in PDF.
- Explicit table models add most value on grid reconstruction, merged headers, and cell topology. They should be composed with, not conflated with, cell transcription and business-semantic extraction.
- Use graph/partial-order semantics internally where sequence ambiguity matters; linearize only at the export boundary with a documented deterministic policy.

### Gaps

- The methods above are not uniformly evaluated on the same inputs, compute budgets, or output contracts; headline results across papers are not directly comparable.
- Published benchmark scores do not establish safe performance on all languages, handwriting, degraded scans, RTL, unusual forms, or tables spanning pages.

## Which benchmarks and measures fit which inputs, and what do they omit or bias?

### Takeaway

No single benchmark covers native PDFs, scanned OCR, layout boxes, reading order, receipt fields, table grids, and final Markdown serialization equally well. Use a task-stratified evaluation portfolio: native-PDF text extraction, OCR/recognition on image inputs, layout detection, reading order, table structure, domain-specific extraction, and end-to-end multi-page conversion. Keep document-level splits and document provenance; report per-slice metrics and the actual evaluator/serialization conventions.

### Cited Findings

- **Native PDFs / text extraction.** Bast and Korzen create a TeX-to-PDF parallel corpus of 12,098 arXiv scientific articles to evaluate PDF text extraction, noting PDFs encode glyph positions rather than semantic units/roles. It is particularly relevant for native text extraction and grouping/order, but arXiv science is not representative of receipts, scanned forms, or arbitrary office PDFs. — [Bast & Korzen, JCDL 2017](https://doi.org/10.1109/JCDL.2017.7991564), [benchmark paper](https://ad-publications.cs.uni-freiburg.de/benchmark.pdf).
- **Scanned layout / region detection.** DocLayNet has 80,863 pages from six document categories and 11 bounding-box classes, with human annotations; use it for visual page-layout detection/generalization rather than OCR transcription, table-cell correctness, or end-to-end Markdown. PubLayNet is much larger (364k+ pages) but is scientifically skewed and aligned to PubMed XML; DocBank has 500k weakly supervised token-level labels derived from arXiv LaTeX. This makes the trio complementary: broad scale/weak labels vs human-curated layout variety, not interchangeable. — Birgit Pfitzmann et al., “DocLayNet,” ACM SIGKDD 2022 (paper DOI [10.1145/3534678.3539043](https://doi.org/10.1145/3534678.3539043), [official repo](https://github.com/DS4SD/DocLayNet)); Xu Zhong et al., “PubLayNet,” ICDAR 2019, [DOI 10.1109/ICDAR.2019.00166](https://doi.org/10.1109/ICDAR.2019.00166); Minghao Li et al., “DocBank,” COLING 2020, [ACL](https://aclanthology.org/2020.coling-main.82/).
- **Receipt/form extraction.** FUNSD is a small noisy scanned-form dataset for form understanding; CORD and SROIE target receipt parsing/extraction. These are useful for schema-specific semantic extraction (entity labels/relations and receipt fields) and model comparisons under those schemas, but their field taxonomies and template/domain distributions do not measure generic document conversion. A model with high entity F1 may still fail to transcribe all text or serialize layout. — Guillaume Jaume et al., “FUNSD: A Dataset for Form Understanding in Noisy Scanned Documents,” ICDARW 2019, [DOI 10.1109/ICDARW.2019.10029](https://doi.org/10.1109/ICDARW.2019.10029); Seunghyun Park et al., “CORD: A Consolidated Receipt Dataset for Post-OCR Parsing,” NeurIPS Workshop 2019, [arXiv: 2011.08858](https://arxiv.org/abs/2011.08858); Zheng Huang et al., “ICDAR 2019 Competition on Scanned Receipt OCR and Information Extraction,” ICDAR 2019, [DOI 10.1109/ICDAR.2019.00244](https://doi.org/10.1109/ICDAR.2019.00244).
- **OCR and document VQA are not parser-completeness metrics.** OCRBench spans recognition, scene-text VQA, document VQA, key-information extraction, and handwritten mathematical expression recognition; its manual benchmark subset contains 1,000 QA pairs (the associated paper aggregates 29 datasets). OCRBench v2 expands to 31 scenarios and 10,000 human-verified QA pairs, including localization and reasoning. DocVQA has 50,000 questions over 12,000+ document images. These test selected answers/capabilities, not exhaustive transcription, order of all blocks, or lossless structural conversion. Accuracy/ANLS also permits answer variants and can overlook omitted context. — Canjie Luo et al., “OCRBench: On the Hidden Mystery of OCR in Large Multimodal Models,” *Science China Information Sciences* 2024, [DOI 10.1007/s11432-024-4235-6](https://doi.org/10.1007/s11432-024-4235-6), [arXiv:2305.07895](https://arxiv.org/abs/2305.07895); [Fu et al., OCRBench v2, NeurIPS 2025](https://proceedings.neurips.cc/paper_files/paper/2025/hash/8c2e6bb15be1894b8fb4e0f9bcad1739-Abstract-Datasets_and_Benchmarks_Track.html); [Mathew et al., DocVQA, WACV 2021](https://openaccess.thecvf.com/content/WACV2021/html/Mathew_DocVQA_A_Dataset_for_VQA_on_Document_Images_WACV_2021_paper.html).
- **Table benchmarks.** PubTabNet uses scientific tables paired with HTML and popularizes TEDS (tree edit distance similarity) for table structure/content; PubTables-1M adds detailed table-cell geometry, headers, canonicalized structure and supports GriTS topology/content/location. FinTabNet is relevant to financial-report tables, while SciTSR targets scientific table structure. Use at least one non-scientific/financial slice: high PubTables performance does not guarantee invoices or irregular business tables. Table text, table grid, table detection, and table-to-semantic-record extraction need separate reporting. — Xu Zhong et al., “PubTabNet: Towards the Future of Dataset for…,” ICDAR 2019, [arXiv:1911.10683](https://arxiv.org/abs/1911.10683); [Smock et al., PubTables-1M](https://openaccess.thecvf.com/content/CVPR2022/html/Smock_PubTables-1M_Towards_Comprehensive_Table_Extraction_From_Unstructured_Documents_CVPR_2022_paper.html); [GriTS](https://arxiv.org/abs/2203.12555); [official Table Transformer repo](https://github.com/microsoft/table-transformer).
- **Reading order benchmarks.** ReadingBank’s 500k Word-derived pages support large-scale sequence prediction, but the derivation from Word XML can encode authoring order rather than independently judged human reading preference. OmniDocBench includes reading-order annotations and per-document/layout analysis, and the 2024 relation-modeling work argues that ordering relations can better represent ambiguous/incomplete orders than a single sequence. Report exact sequence metrics alongside pairwise precedence/relation F1, and explicitly define excluded elements (e.g. headers, captions, figures). — [ReadingBank](https://github.com/doc-analysis/ReadingBank); [Zhang et al., EMNLP 2024](https://aclanthology.org/2024.emnlp-main.540/); [Ouyang et al., CVPR 2025](https://openaccess.thecvf.com/content/CVPR2025/html/Ouyang_OmniDocBench_Benchmarking_Diverse_PDF_Document_Parsing_with_Comprehensive_Annotations_CVPR_2025_paper.html).
- **OmniDocBench: strongest single public end-to-end starting point, not a complete production proxy.** The CVPR 2025 benchmark paper describes diverse pages from nine sources and fine-grained layout, text, formula, table, attributes and reading-order labels; repository versions have grown (current repo describes 1,651 pages; earlier paper/release materials discuss 1,355/1,475-page versions). Pin the exact version and evaluator. Its multidimensional/attribute analysis helps isolate errors, while its overall scores still depend on defined canonical Markdown/LaTeX/HTML and matching rules. It is primarily page-level and cannot alone test document-wide heading hierarchy, repeated headers across pages, cross-page tables, or business-specific extraction. — Linke Ouyang et al., “OmniDocBench: Benchmarking Diverse PDF Document Parsing with Comprehensive Annotations,” CVPR 2025, pp. 24838–24848, [CVF paper](https://openaccess.thecvf.com/content/CVPR2025/html/Ouyang_OmniDocBench_Benchmarking_Diverse_PDF_Document_Parsing_with_Comprehensive_Annotations_CVPR_2025_paper.html), [arXiv](https://arxiv.org/abs/2412.07626), [versioned official repository](https://github.com/opendatalab/OmniDocBench).
- **olmOCR-bench and unit tests.** olmOCR-bench contains 1,403 PDFs and 7,010 tests covering text presence/absence, order, tables, math, headers/footers and small text. Assertions on concrete content/relationships can be more robust than exact output-string match; benchmark tests are still hand/automatically selected, English-oriented and not exhaustive. — [official olmOCR-bench dataset card](https://huggingface.co/datasets/allenai/olmOCR-bench); Poznanski et al., [olmOCR 2](https://arxiv.org/abs/2510.19817).
- **End-to-end structured extraction / multi-page.** READoc frames multi-page PDFs to semantically rich Markdown and evaluates text, heading, table and reading-order components; its authors identify fragmentation and single-page evaluation as limitations of prior benchmarks. It is a useful complement for document-level hierarchy, but its arXiv-derived source construction and auto-conversion pipeline should be audited for source and annotation artifacts. — “READ: A Unified Benchmark for Realistic Document Structured Extraction,” Findings of ACL 2025, [ACL Anthology](https://aclanthology.org/2025.findings-acl.1128/).
- **Newer leak-aware/source-traceable benchmarks (as of cutoff).** PureDocBench (2026 preprint) generates pages from fresh HTML/CSS, keeps source-traceable annotations, allows regeneration and includes clean/degraded/realistic conditions specifically to reduce known overlap risk. It is promising for controlled tests but synthetic rendering cannot cover every naturally occurring PDF artifact. ParseBench (2026 preprint) targets enterprise pages and semantic table/content/formatting/grounding checks, addressing weaknesses of raw Markdown string matching, but should be treated as emerging rather than an established cross-community standard. — “How Far Is Document Parsing from Solved? PureDocBench,” arXiv:2605.07492 (2026), [arXiv](https://arxiv.org/abs/2605.07492); “ParseBench: A Document Parsing Benchmark for AI Agents,” arXiv:2604.08538 (2026), [arXiv](https://arxiv.org/abs/2604.08538).
- **Metric caveats.** Character/word edit distance and CER/WER quantify transcription differences but do not tell whether a table grid or semantic relation is right. mAP/IoU scores localize boxes/classes but not order, full text, grouping, or semantics. TEDS compares HTML tree similarity and GriTS evaluates table matrix topology/content/location, but each depends on canonical cell segmentation and normalization. VQA exact match/ANLS measures answers, not complete parses. Markdown edit distance can penalize semantically equivalent table tags, heading styles or harmless whitespace and may under-penalize a critical numeric value error in a long page. Complement automated measures with targeted invariants and review of sampled failures. — [GriTS paper](https://arxiv.org/abs/2203.12555); [PubTables-1M paper](https://openaccess.thecvf.com/content/CVPR2022/html/Smock_PubTables-1M_Towards_Comprehensive_Table_Extraction_From_Unstructured_Documents_CVPR_2022_paper.html); [OmniDocBench paper](https://openaccess.thecvf.com/content/CVPR2025/html/Ouyang_OmniDocBench_Benchmarking_Diverse_PDF_Document_Parsing_with_Comprehensive_Annotations_CVPR_2025_paper.html).
- **Leakage and benchmark provenance.** Layout/model benchmarks built from arXiv, PubMed or web documents may overlap with pretraining sources; randomly split pages from the same source document/template can also leak style or text. The contamination literature distinguishes exact and near-duplicate overlap and warns that public static test sets can overstate generalization. Split at document/source/template level, deduplicate by content and rendered-page similarity, document source dates, and keep a small prospective/private holdout. Public benchmark leaderboard scores alone cannot verify that a model's pretraining data are clean. — Aparna Elangovan, Jiayuan He, and Karin Verspoor, “Memorization vs. Generalization: Quantifying Data Leakage in NLP Performance Evaluation,” EACL 2021, [ACL Anthology](https://aclanthology.org/2021.eacl-main.113/); Hyeong Kyu Choi et al., “How Contaminated Is Your Benchmark?,” ICML 2025, [PMLR](https://proceedings.mlr.press/v267/choi25b.html); [PureDocBench](https://arxiv.org/abs/2605.07492).
- **Benchmark-specific recommendation (inference):** for a fastdocparse-like parser, use the native-PDF corpus for token/word recall, block grouping and order; include DocLayNet for visual element class/box; include PubTables-1M plus PubTabNet and a financial/receipt-table slice for grid/content; include CORD/SROIE/FUNSD only when KIE is an intended task; evaluate OmniDocBench end-to-end and olmOCR-bench unit tests for broad PDF page stress; add a small private multi-page corpus with scanned docs and actual production layouts. Do not collapse all into one weighted score until product priorities and acceptable failures are explicitly set.

### Inferences

- Report quality by input route: native text PDF, scanned image PDF, mixed/embedded image, and digitally malformed PDF. Otherwise excellent native extraction may mask poor OCR and vice versa.
- At minimum separate page/element detection (precision/recall/AP), transcription (CER/WER or normalized edit distance), reading order (normalized edit distance plus precedence-pair accuracy), table grid (GriTS topology/location and content, or TEDS/TEDS-S), semantic fields (entity/relation F1 or exact field accuracy), and end-to-end serialization (content omissions, structure invariants, output usability).
- Hold out whole documents, not pages. For recurring templates, make a template-family split too. Deduplicate not only document filenames but exact/near-identical text and page images. Refresh a private evaluation set as public model training data and benchmark releases evolve.
- For table-rich production use, include error-weighted measures for numeric cell correctness and header/value association; a high average table score can conceal rare but high-impact wrong digits.

### Gaps

- Public benchmark provenance and exact training-data overlap are usually unknowable for closed models, and sometimes only partially known for open models; report this as uncertainty rather than asserting leakage/no leakage.
- There is no broadly accepted public benchmark that jointly covers arbitrary multi-page native PDFs, scanned documents, table semantics, all reading-order ambiguities, and user-specific Markdown/JSON utility.

## What hybrid architecture is evidence-supported for a lightweight parsing library with native positioned text, OCR, and separate LLM extraction?

### Takeaway

Evidence and the modular systems literature favor a staged, confidence-aware hybrid rather than replacing every input with full-page OCR or relying on one end-to-end LLM to infer everything: use native PDF text and geometry as the fast/default path; detect pages or regions needing OCR; retain positioned tokens; apply selective layout/table analysis; build an explicit structured intermediate representation; serialize deterministically; keep the separate LLM extraction stage downstream, grounded in source spans/cells and given visual context only when text/layout evidence is insufficient.

### Cited Findings

- Docling demonstrates an efficient local modular design combining PDF backends, a layout detector, OCR, TableFormer, a typed document representation and post-processing for reading order/caption links; the report describes reusing PDF text tokens to associate table-cell structure and avoid re-transcribing cell text. It also explicitly treats Markdown/HTML as lossy export from richer JSON/document objects. — Auer et al., [Docling Technical Report](https://arxiv.org/abs/2408.09869), [full text](https://arxiv.org/html/2408.09869v3); Nassar et al., [TableFormer](https://openaccess.thecvf.com/content/CVPR2022/html/Nassar_TableFormer_Table_Structure_Understanding_With_Transformers_CVPR_2022_paper.html).
- TableFormer’s integration strategy is direct precedent for combining visual table structure with programmatic PDF text, rather than making a vision model re-read legible native text. — [TableFormer CVPR 2022](https://openaccess.thecvf.com/content/CVPR2022/html/Nassar_TableFormer_Table_Structure_Understanding_With_Transformers_CVPR_2022_paper.html); [Docling model architecture](https://arxiv.org/html/2408.09869v3).
- Donut’s motivation identifies OCR cost and error propagation as issues in cascaded extraction, but its task-conditioned image-to-structured-output approach trades away explicit OCR token coordinates by default. It provides a useful optional route for specialized image-only extraction tasks, not an argument to discard reliable PDF text. — Kim et al., [Donut ECCV 2022](https://arxiv.org/abs/2111.15664).
- Dolphin provides recent evidence for a hybrid within visual parsing itself: identify ordered layout elements, then parse elements in parallel with task-specific prompts rather than autoregressively producing the entire page as one long output. This suggests selective element-level escalation can reduce output coupling, although a 0.3B visual parser still adds runtime/model dependency beyond a lightweight library's base path. — Feng et al., [Dolphin Findings ACL 2025](https://aclanthology.org/2025.findings-acl.1130/).
- olmOCR emphasizes batch-scale costs and visually grounded PDF parsing, while its benchmark converts quality goals into local tests (e.g., text present, order constraints, table/math properties). This supports explicit validation and failure reporting around any model-powered fallback. — Poznanski et al., [olmOCR](https://arxiv.org/abs/2502.18443); [olmOCR-bench](https://huggingface.co/datasets/allenai/olmOCR-bench).
- The separate tasks in benchmarks imply that OCR, layout, reading order, table structure and KIE should remain separately testable modules/contracts; layout-aware encoders like LayoutLM can help entity extraction but do not supply a general serialization layer. — Xu et al., [LayoutLM KDD 2020](https://doi.org/10.1145/3394486.3403172); Huang et al., [LayoutLMv3 ACM MM 2022](https://arxiv.org/abs/2204.08387); Ouyang et al., [OmniDocBench CVPR 2025](https://arxiv.org/abs/2412.07626).

### Inferences

- **Recommended design (inference from cited architectures and task boundaries):**
  1. **Classify input/page evidence.** Detect usable native text, image-only/scanned regions, mixed pages, broken character mappings and likely malformed ordering. Use existing positioned tokens as observations and preserve the original source coordinates.
  2. **Native-first extraction.** Reconstruct lines/blocks from glyph or word boxes using geometry, font/style and whitespace; use lightweight column/region heuristics for straightforward pages. Avoid rasterizing pages for OCR when text is reliably available.
  3. **Selective OCR fallback.** OCR scanned pages or image regions and only retry low-confidence or absent/invalid text regions. Preserve provenance (`native`, `OCR`, `corrected`) and confidence for every token. Never silently replace native text with a visually generated transcription.
  4. **Layout and ordering as explicit structural inference.** Identify region classes (text, heading, table, figure/caption, header/footer, list, formula) and group tokens. Keep layout graph/relations and region boxes in an intermediate representation; compute a deterministic order for serialization. Preserve alternative or uncertain orders where appropriate.
  5. **Specialized table path.** Detect table candidates, recover row/column/cell topology and spans, then align cells with native positioned text first and OCR text second. Return structured cells, boxes, header roles and source token references; validate row/column consistency. Allow plain text fallback when confidence is low rather than emitting fabricated grids.
  6. **Typed document IR before Markdown.** Store ordered blocks with type, bounding box, page, source text/tokens, confidence, relations, table grid, and metadata. Derive JSON as the rich representation and Markdown as a configurable lossy view; retain HTML for complex tables if requested. Use stable defaults for headings, headers/footers, captions, formulas and page boundaries.
  7. **LLM extraction is a distinct downstream consumer.** Pass relevant blocks/cells plus their source coordinates/text, request schema-constrained values and citations back to block/cell IDs, and validate outputs against source evidence. Route a page crop to a multimodal model only for ambiguous visual cases or task-specific extraction where the model's visual grounding has measurable benefit. Do not let semantic extraction mutate the base transcription silently.
  8. **Confidence, abstention and auditability.** Emit per-stage confidence and structured warnings for unresolved order, OCR alternatives, table ambiguity, missing content and unsupported format. Permit downstream users to select speed/accuracy modes and retain the original parsed elements for review.
  9. **Evaluation gates.** Benchmark native-PDF and scanned routes separately; add ablations (native-only, OCR fallback, layout, table model, LLM visual fallback), report latency/memory as well as quality, use document/template-disjoint splits, and run explicit tests for content omission, reading-order constraints, cell-header association and JSON/Markdown invariants.
- This design minimizes unnecessary model work while preserving a path to specialist vision models. It is an architectural recommendation, not a claim that the specific module combination has been benchmarked end-to-end in this repository.

### Gaps

- Without inspecting the repository (explicitly excluded by the assignment), these recommendations cannot confirm which token-confidence signals, page rendering hooks, serialization contracts or feature flags already exist; the connection to fastdocparse must remain high-level.
- Literature establishes complementary systems and metrics, but does not establish a universally best threshold for OCR fallback, whether a compact table model is worth its dependency cost, or which IR is optimal for fastdocparse's consumers. Those are empirical product tradeoffs to measure on the project's own corpus.
