# LangExtract internals (as of Nov. 12, 2026)

## Is LangExtract a PDF/page-layout parser, or an LLM-assisted text extraction library?

### Takeaway

LangExtract is primarily a text-in, structured-information-out LLM orchestration and source-alignment library—not a PDF parser, OCR engine, or page-layout analyzer. It can accept text in a `Document` wrapper and optionally fetch a URL as text; PDF/document parsing and OCR are upstream responsibilities (or supplied by third-party integrations such as `langextract-docling`). Its character grounding is against the supplied text string, not PDF pages or bounding boxes.

### Cited Findings

- The official repository describes LangExtract as a Python library that uses LLMs to extract structured information from unstructured **text documents**; its end-to-end diagram describes unstructured text being chunked, sent to an LLM, then grounded to source character spans. [Repository README](https://github.com/google/langextract/blob/main/README.md)
- The public `extract()` API accepts `str | Iterable[Document]`; `Document` stores raw `text`, an optional ID, and additional prompt context. There is no PDF/image/file-object input type in this API. [Source: `langextract/extraction.py`](https://github.com/google/langextract/blob/main/langextract/extraction.py); [Source: `langextract/core/data.py`](https://github.com/google/langextract/blob/main/langextract/core/data.py)
- `fetch_urls=True` fetches an HTTP(S) URL and passes the downloaded content as text. It is not a URL-to-PDF/document conversion layer: the implementation warns if content type is not text-like, then decodes bytes to a string. URL fetching is opt-in and the API documentation explicitly warns of SSRF risks. [Source: `langextract/io.py`](https://github.com/google/langextract/blob/main/langextract/io.py); [Source: `langextract/extraction.py`](https://github.com/google/langextract/blob/main/langextract/extraction.py)
- The core repository still tracks native PDF/document integration separately. Issue #184 proposes Docling as an optional front-end, states that current workflows convert files to text before feeding LangExtract, and as of its Nov. 6, 2026 update still describes the proposal as not closing the broader native PDF-support request. A community `langextract-docling` wrapper exists, but is separate from Google’s core package. [Official issue #184 and updates](https://github.com/google/langextract/issues/184)
- Google’s Document AI Layout Parser is a distinct service/product: it parses files, uses OCR and Gemini capabilities, identifies layout elements (tables, figures, headings, lists), preserves hierarchy, and creates layout-aware chunks. Do not attribute those capabilities to LangExtract merely because both projects are from Google or use LLMs. [Document AI Layout Parser docs](https://docs.cloud.google.com/document-ai/docs/layout-parse-chunk)
- Docling is explicitly a document-conversion/parsing project: its README lists diverse input formats, advanced PDF layout/reading-order/table understanding and OCR, while its `DoclingDocument` format can preserve document hierarchy, layout/bounding boxes, and provenance. These are structurally different capabilities from LangExtract’s text character intervals. [Docling README](https://github.com/docling-project/docling); [DoclingDocument docs](https://docling-project.github.io/docling/concepts/docling_document/)
- As of the research date, the latest official LangExtract release is **v1.7.2**, released Nov. 7, 2026. The release changes include URL-fetch/file-encoding fixes and visualization hardening, not a core PDF/layout-parser feature. The checked-in `pyproject.toml` on `main` also reports version `1.7.2`. [Release v1.7.2](https://github.com/google/langextract/releases/tag/v1.7.2); [Source: `pyproject.toml`](https://github.com/google/langextract/blob/main/pyproject.toml)

### Inferences

- LangExtract should be understood as an extraction/alignment stage that consumes text made available by a parser. Docling or another parser can produce text while preserving layout/provenance; LangExtract can then extract task-specific entities/relations from that text. A separate mapping is required to translate its character positions back to page regions unless the upstream integration explicitly preserves and maps provenance.
- “Source grounded” here means an extraction span can be located in the text string passed to LangExtract. It does not establish that OCR read the PDF correctly, that the source text came from the right page/column, or that a semantically inferred attribute is factually true.

### Gaps

- The core repository does not document a native binary-PDF or page-layout input path in the reviewed API. The separate wrapper’s feature coverage/provenance guarantees are not assumed to be equivalent to core behavior.

## How does LangExtract handle input, chunking, prompting/schema, alignment, and results?

### Takeaway

The main pipeline takes text, splits it into sentence/token-aware character-bounded chunks, renders each chunk with user instructions and few-shot examples, calls a selected LLM provider in batches (optionally with multiple passes), parses the structured response, then aligns returned extraction strings back to the chunk and offsets those spans into the original text. The returned object is an annotated text document—not a parsed PDF or page-layout tree.

### Cited Findings

- **Input and document model:** `extract(text_or_documents=...)` handles a string or iterable of `Document`s. Each `Document` contains `text`, an optional `document_id`, and `additional_context`; its tokenized representation is cached/computed from that text. String input returns one `AnnotatedDocument`; a `Document` iterable returns a list. [Source: `langextract/extraction.py`](https://github.com/google/langextract/blob/main/langextract/extraction.py); [Source: `langextract/core/data.py`](https://github.com/google/langextract/blob/main/langextract/core/data.py)
- **URL and file adapters:** URLs are fetched only when `fetch_urls=True`; strings are otherwise treated literally. `io.Dataset` currently loads CSV rows into `Document(text, document_id)` objects, while annotated results are serialized/deserialized as JSON Lines. This CSV dataset loader is not a PDF/document parser. [Source: `langextract/io.py`](https://github.com/google/langextract/blob/main/langextract/io.py)
- **Chunking:** The default `max_char_buffer` in the current extraction API is 1,000 characters. The chunk iterator tries to keep sentence boundaries, packs multiple sentences when possible, splits long sentences at token/newline boundaries to fit, and allows a single oversized token to exceed the buffer. It records token and character intervals back to the source document. [Source: `langextract/extraction.py`](https://github.com/google/langextract/blob/main/langextract/extraction.py); [Source: `langextract/chunking.py`](https://github.com/google/langextract/blob/main/langextract/chunking.py)
- **Batching and context:** Chunks are processed in batches (`batch_length` default 10) with parallel workers (`max_workers` default 10); effective concurrency is bounded by both. `context_window_chars` can add the tail of a previous chunk for the same document to help with cross-chunk coreference. `extraction_passes` defaults to 1; extra sequential passes can improve recall but reprocess text and increase model/API token costs. [Source: `langextract/extraction.py`](https://github.com/google/langextract/blob/main/langextract/extraction.py); [Source: `langextract/annotation.py`](https://github.com/google/langextract/blob/main/langextract/annotation.py); [Source: `langextract/prompting.py`](https://github.com/google/langextract/blob/main/langextract/prompting.py)
- **Prompting and examples:** A user supplies `prompt_description` and typically one or more `ExampleData(text, extractions)` examples. Each `Extraction` example has an `extraction_class`, verbatim `extraction_text`, and optional attributes. Prompt generation constructs an instruction, optional additional context, examples in Q/A form, and the current chunk as the question. Few-shot examples are required unless an `output_schema` is provided; examples remain useful prompt guidance even when the explicit output schema is used. The API validates example-to-source alignment by default and warns on questionable matches. [Source: `langextract/prompting.py`](https://github.com/google/langextract/blob/main/langextract/prompting.py); [Source: `langextract/core/data.py`](https://github.com/google/langextract/blob/main/langextract/core/data.py); [Source: `langextract/extraction.py`](https://github.com/google/langextract/blob/main/langextract/extraction.py); [README quick start](https://github.com/google/langextract/blob/main/README.md)
- **Structured output:** The default serialized envelope uses a top-level `extractions` array. LangExtract can derive provider constraints from examples; in the current API explicit JSON `output_schema` support is documented for Gemini and OpenAI. Format handling supports JSON/YAML model output, with fence behavior configured/selected according to provider/schema capabilities. Ollama is a built-in local provider but the README says it does not currently support user-supplied `output_schema`. [Source: `langextract/extraction.py`](https://github.com/google/langextract/blob/main/langextract/extraction.py); [Provider documentation](https://github.com/google/langextract/blob/main/langextract/providers/README.md); [Output schema example](https://github.com/google/langextract/blob/main/docs/examples/output_schema.md); [README](https://github.com/google/langextract/blob/main/README.md)
- **Model backends:** The core offers Gemini and Ollama providers; OpenAI is built in behind an optional extra, and a plugin/entry-point system allows external providers. Provider choice is separate from document parsing. [Provider documentation](https://github.com/google/langextract/blob/main/langextract/providers/README.md); [Source: `pyproject.toml`](https://github.com/google/langextract/blob/main/pyproject.toml)
- **Parsing model output and grounding:** The resolver parses JSON/YAML into `Extraction` objects and then `WordAligner` searches the current chunk text. Exact token matches are attempted first; fuzzy matching can be enabled and uses a threshold (default 0.75) plus density controls. Alignment records token and character intervals and a status (`MATCH_EXACT`, `MATCH_LESSER`, or `MATCH_FUZZY`). The chunk’s starting offsets are added so intervals point into the full document text. If the returned string cannot be located, its `char_interval` remains `None`. [Source: `langextract/resolver.py`](https://github.com/google/langextract/blob/main/langextract/resolver.py); [Source: `langextract/core/data.py`](https://github.com/google/langextract/blob/main/langextract/core/data.py); [Source: `langextract/annotation.py`](https://github.com/google/langextract/blob/main/langextract/annotation.py)
- **Output objects:** `AnnotatedDocument` carries the original `text`, `document_id`, and a list of `Extraction`s. Each extraction holds class, text, optional attributes/description, extraction/group indices, token interval, character interval and alignment status. There are no core page numbers, PDF coordinates, bounding boxes, or layout hierarchy in these types. [Source: `langextract/core/data.py`](https://github.com/google/langextract/blob/main/langextract/core/data.py)
- **Persistence and visualization:** `save_annotated_documents` writes JSONL; `load_annotated_documents_jsonl` restores objects. `visualize()` accepts an `AnnotatedDocument` or JSONL path and builds interactive HTML with class-colored highlights, navigation and attribute display. It filters out extractions without valid character intervals; with a JSONL path it visualizes the first document. This visualization highlights original text, not a PDF page image. [Source: `langextract/io.py`](https://github.com/google/langextract/blob/main/langextract/io.py); [Source: `langextract/visualization.py`](https://github.com/google/langextract/blob/main/langextract/visualization.py); [README visualization example](https://github.com/google/langextract/blob/main/README.md)
- **Additional supported data formats:** The documented core adapter surface includes CSV input for tabular text datasets and JSONL result persistence; JSON/YAML refer to model-output formatting. The core `extract()` function itself does not accept PDF, DOCX, image, HTML, or DoclingDocument objects as inputs. [Source: `langextract/io.py`](https://github.com/google/langextract/blob/main/langextract/io.py); [Source: `langextract/extraction.py`](https://github.com/google/langextract/blob/main/langextract/extraction.py)

### Inferences

- The alignment algorithm provides useful audit hooks but it is a post-generation text matching procedure, not a guarantee that every extracted claim is supported. For instance, extraction attributes can be inferred per prompt/model and are not separately assigned evidence spans; a value from a few-shot example or a paraphrase may fail alignment and have no interval. The README itself cautions that LLM world knowledge may be used and that unlocatable outputs get `char_interval=None`. [README grounding and world-knowledge notes](https://github.com/google/langextract/blob/main/README.md)
- Character offsets only remain meaningful relative to the exact text passed in (including OCR/normalization, line ordering, and any conversion artifacts). If upstream parsing changes that text, a parser-to-source provenance map is needed to recover page/geometry locations.

### Gaps

- The official API documents the text intervals and alignment status but does not claim that fuzzy matches are semantic verification or that the offsets correspond to visual page coordinates.

## How should we compare LangExtract with Docling and our separate parsing/extraction phases?

### Takeaway

Treat Docling and LangExtract as complementary stages, not interchangeable parsers: Docling addresses file ingestion, OCR/layout reconstruction and a structured document representation; LangExtract addresses task-specific LLM extraction from supplied text, with text-span alignment. In an architecture that already separates parsing from extraction, LangExtract belongs mainly in the extraction phase, downstream of parsing (with an adapter/provenance bridge if page-level traceability matters).

### Cited Findings

- Docling’s official README describes multi-format conversion, advanced PDF understanding (page layout, reading order, tables, formulas, images), OCR for scanned PDFs, and conversion into the unified `DoclingDocument` representation. [Docling README](https://github.com/docling-project/docling)
- `DoclingDocument` represents text, tables, pictures and key-value items; hierarchical body/furniture/groups; reading order; and layout/bounding boxes and provenance when available. [DoclingDocument documentation](https://docling-project.github.io/docling/concepts/docling_document/)
- LangExtract’s official issue discussing Docling integration specifically sketches the two-stage flow: Docling produces document content/provenance, then text is supplied to LangExtract, with extracted spans mapped back through provenance. The issue identifies the integration as a proposal/third-party or optional front-end rather than a built-in parsing subsystem. [LangExtract issue #184](https://github.com/google/langextract/issues/184)
- Google Document AI Layout Parser is a separate service and another example of an actual layout parser: it detects document elements and hierarchy, performs OCR/layout analysis, and generates context-aware chunks. It is not LangExtract. [Document AI Layout Parser docs](https://docs.cloud.google.com/document-ai/docs/layout-parse-chunk)
- The LangExtract release notes identify v1.7.2 as the latest release on Nov. 7, 2026; core package dependencies and API are consistent with an LLM extraction library rather than a PDF parser (no PDF parser is exposed in the `extract()` input contract). [Release v1.7.2](https://github.com/google/langextract/releases/tag/v1.7.2); [Source: `langextract/extraction.py`](https://github.com/google/langextract/blob/main/langextract/extraction.py)

### Inferences

- A clean phase boundary for our pipeline is: **parsing** converts source files into canonical text/structure and retains page/element provenance; **extraction** receives text or parser-produced text segments and extracts the requested schema/entities/relations. LangExtract is an option for the latter, not a substitute for the former.
- For simple text-first use, pass a full text string or `Document` and use LangExtract’s own chunking/alignment. For layout-sensitive use, parse with Docling (or another parser), then decide whether to pass the whole linearized text or separate chunks/documents. Preserve a mapping between each parser text segment and its page/item coordinates; LangExtract’s own offsets alone do not recover that mapping.
- Docling and LangExtract have different output contracts: Docling’s output is a rich document structure with layout/provenance, while LangExtract’s output is an `AnnotatedDocument` containing typed extraction values and character intervals. A combined pipeline needs an explicit adapter and a decision about whether to preserve Docling provenance through serialization.
- Do not conflate extraction’s character grounding with Document AI Layout Parser’s layout parsing or with Docling’s layout-aware OCR. LangExtract can organize text values into user-defined classes/attributes; it does not by itself identify columns, read order, table cells, figures, or page boxes.

### Gaps

- This comparison establishes the official project boundary and a conceptual placement in separate parsing/extraction phases. The exact integration points and data contracts in our local parsing/extraction implementation are outside this LangExtract investigation and should be validated against those modules before implementation.
