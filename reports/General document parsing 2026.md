# Build A Parser That Preserves Evidence

The right design for varied documents is a staged, hybrid parser that keeps source evidence intact and derives simpler views from it—not a universal text-flattening pass or a mandatory vision model. Fastdocparse already has a useful base in normalized page geometry, nested text and table elements, provenance, and an optional PDF inspection path; the next step is to make that representation relational and stable, route pages between native extraction and OCR, and benchmark errors before adding heavyweight models. Keep tables as grids and figures as retained image regions with caption links, represent reading order as a potentially ambiguous relation, and provide canonical JSON alongside readable Markdown and source-grounded chunks. This preserves the lightweight path for clean PDFs while creating an extensible route for scans and complex layouts. The available research motivates these design choices, but does not establish one best engine or prove generality on this repository’s small, customs-oriented corpus.

## Layout diversity makes evidence-preserving hybrid parsing the safer default

General-purpose parsing cannot assume that document appearance or source order is consistent. DocLayNet’s 80,863 human-annotated pages span six document categories and were designed to address the limited layout diversity of scientific-paper datasets; however, its authors minimized scans and excluded receipts, invoices, handwriting, and text-in-the-wild photos. It supports training and evaluating on varied layouts, not a claim that a model trained on it will generalize to all business documents ([1]). PDF text extraction has a complementary limitation: content-stream order can differ from natural reading order, and simple top-to-bottom sorting is only a heuristic ([2]).

Use a staged pipeline: inspect each page’s metadata, text-layer coverage, geometry, image occupancy, tags, and rotation; choose native text, OCR, or a hybrid route at page or region level; then perform layout grouping and relation inference without overwriting raw evidence. Native PDF text and vector geometry are fast and precise for born-digital content, while rendered-page OCR and visual models can recover evidence missing from scans. Hybrid extraction is important because a PDF can contain both digital text and scanned regions. OCR preprocessing should account for rotation and skew, which can impair line segmentation ([3]). Keep OCR and learned layout backends optional: they raise install, runtime, model-asset, and maintenance costs, and the research notes found no comparable end-to-end benchmark establishing a universal winner among converters. Docling’s pipeline is a useful precedent for combining positioned PDF text with page images and AI layout/table models, but its reported timings and quality are specific to its implementations and settings ([4]).

This direction fits the repository’s stated lightweight, text-first value proposition. The existing parser already creates normalized bounding boxes, nested block/line/word elements, provenance, and table cells; its native PDF path uses PyMuPDF table finding and a conservative heuristic for simple unruled tables ([5], [6]). But the README says scanned PDFs are not connected to positioned OCR in the inspect command, while current OCR ingestion primarily returns text rather than geometry-preserving word structures ([5]). The next implementation should therefore improve the evidence contract and route coverage before making an optional vision model the default.

## A versioned element graph should preserve order, tables, and figures

Extend the existing page-and-element representation into a canonical, versioned document model: document metadata and diagnostics; pages with dimensions, coordinate units, rotation, and coordinate frame; elements with stable IDs, type, text or asset reference, geometry, children, source order, provenance, confidence, and extensible attributes; and typed relations between element IDs. Useful relations include `contains`, `precedes`, `caption_of`, `key_for`, and `continues_on_page`. Keep source/content-stream order distinct from inferred reading order. Recent work models immediate succession as a directed acyclic relation and reports non-linear order in 23.76% of segments in its ROOR sample, illustrating why a single sequence can erase parallel columns or independent page flows ([7]). A deterministic linear reading-order projection can still serve consumers, but should be explicitly marked as derived and preserve conflicts or alternatives.

Tables should remain page-local structures containing ordered rows and cells, row/column indices, bounding boxes, text or references to source words, and row/column spans. Preserve blank cells and distinguish blanks from merged cells; flattening a grid into prose, CSV, or Markdown can discard topology. PubTables-1M formalizes table detection, structure recognition, and functional/header analysis as separable problems, while GriTS measures topology, content, and location separately ([8], [9]). For scanned or difficult tables, an optional detector/structure-recognition backend can propose boxes and cell grids, with OCR/native words aligned into those cells; do not assume a visual model supplies correct cell text. Table Transformer provides separate detection and structure checkpoints, but was archived in September 2026, so adopting it requires pinning dependencies and planning a replacement or maintenance strategy ([10]).

Figures should likewise remain elements even when the parser cannot read their contents. Retain a crop or asset reference, page box, and any caption as a separate text element linked by `caption_of`; optional OCR, chart extraction, or model-generated descriptions should be labeled as derived content rather than presented as source text. This design keeps the image evidence available for later multimodal processing and makes a missing caption different from a missing figure. Generic layout roles such as `text_block`, `table`, `figure`, or `caption` belong in this parser layer; task-specific concepts such as `invoice_total` belong in the extraction schema and should reference their supporting element IDs.

## Generate LLM views from structure, not instead of it

Expose canonical JSON as the round-trip/audit representation, then render Markdown and LLM chunks from that structure. Markdown is convenient for prompts and inspection, but should not be treated as lossless: table spans and figure assets do not fit naturally in it. Docling documents this difference across JSON, HTML, and Markdown serializers, and its chunkers operate on structured elements rather than requiring Markdown-first splitting ([11]). For fastdocparse, a Markdown table can be a useful approximation, while JSON or HTML retains richer table structure; Markdown should include stable figure placeholders or asset links rather than silently dropping visual content.

Chunk first by meaningful boundaries—section, paragraph, list, table, or caption/figure pair—and then enforce the target model’s token limit. Repeat section headings and table headers where needed; keep a table together when it fits, and split larger tables by coherent row groups while carrying table ID, row indices, spans, and cell evidence. Each chunk should retain document ID, element IDs, page range and boxes, section path, provenance, and asset/table references. If an individual element must be split, preserve offsets and a link to its original element. This balances element-first chunking with tokenizer-aware limits, but no cited source establishes a universally optimal chunk size or proves a specific serialization improves fastdocparse extraction accuracy. Evaluate retrieval, prompt size, and evidence recovery for the intended downstream task rather than assuming the format itself improves results ([11], [12]).

## Implement the contract and evaluation before model escalation

The most useful next work in this repository is incremental. First, add stable element IDs, explicit source-order metadata and typed relations to the existing parsed model, while preserving compatibility with current `ParsedElement` consumers. Record page coordinate frame and rotation explicitly, and distinguish absent/unknown information from a negative detection. Add round-trip JSON tests and regression tests for existing PDF parsing. Second, preserve OCR word boxes, confidence, and transforms in the same canonical coordinate system, then add page-level modality diagnostics and a conservative native/OCR/hybrid routing interface. This closes the current gap between text-only OCR ingestion and positioned PDF parsing without forcing a vision dependency.

Third, formalize current table output with explicit cell indices, spans, empty-cell policy, and separate detection/structure/text/role provenance. Benchmark PyMuPDF’s native table detection and current aligned-table heuristic before introducing visual table recognition. The current heuristic is intentionally conservative and has business-pattern assumptions, so keep it auditable and avoid turning its lexical rules into a generic document taxonomy ([6]). Fourth, add figure regions and caption links with retained crop references, then expose JSON and Markdown serializers and evidence-aware chunking. Only after a representative evaluation should an optional learned layout/table backend be selected; measure accuracy, latency, memory, dependency footprint, licensing, maintenance, and output fidelity on the repository’s target documents.

Build a small, manually checked, document-disjoint gold set from the 36-document synthetic-customs corpus described in the research notes, stratified across born-digital, scanned, multi-page, ruled/unruled, and table/figure cases. That set can reveal regressions and prioritize implementation, but cannot establish broad generality because the files are mostly related customs/invoice/packing-list-like documents. For tables, report detection precision/recall at stated IoU thresholds, GriTS topology/content/location, strict span-aware cell accuracy, and OCR text quality separately; slice results by modality and difficult structure. Split by document or template family, not random pages, to avoid near-duplicate layout leakage. Expand later with held-out reports, statements, forms, multilingual scans, and handwriting if those become product targets ([1], [8], [9]).

## Conclusion

The design principle is to make uncertainty and evidence portable: preserve what the source said and where it appeared, attach inferred structure with provenance, and make linear text only one downstream view. That boundary lets fastdocparse remain inexpensive for simple documents while supporting richer parsing when evaluation justifies it. Near-term success is not “understand every document”; it is reliably representing what each backend detected, exposing what it did not, and measuring the failures before expanding the model stack.
