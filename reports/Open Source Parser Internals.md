# Trace Four Parsers From Page To Structure

Yes: the repositories and their documentation expose enough concrete code to trace how parsing becomes structured output, and to compare the choices each system makes about native PDF text, OCR, layout, reading order, tables, and serialization. The important distinction is that they do not all start from the same evidence: Docling and Marker make hybrid native-text/visual routes explicit; MinerU exposes effort tiers, including a native-text path; PP-StructureV3 is primarily an image/page-oriented OCR and document-model pipeline. Each also has a different internal output contract, so Markdown alone is a poor basis for comparing them. The current `fastdocparse` already has a geometry-preserving parse model, but its main extraction ingestion route still hands downstream extraction a text string. The repositories are excellent learning references, not proof that any one parser will produce perfect structure or win on fastdocparse’s documents.

## Four entrypoints reveal four different pipeline shapes

At a high level, the systems can be read as follows. These are conceptual flows rather than promises of a strictly serial, one-page-at-a-time execution: Docling uses worker stages, MinerU processes PDF windows, and Marker and PaddleOCR can batch or stream work.

| System and reviewed baseline | Simple end-to-end path | Architectural emphasis |
|---|---|---|
| **Docling `v2.150.0`** | Input → `DocumentConverter` routes format/backend/pipeline → PDF backend supplies native text/geometry plus rendered pages → preprocessing, layout, OCR, postprocessing, table recognition, page assembly and reading-order work → `DoclingDocument` → Markdown/HTML/JSON or chunker. | Configurable conversion pipeline with a typed document representation; native and visual evidence can complement each other. ([converter](https://github.com/docling-project/docling/blob/v2.150.0/docling/document_converter.py), [standard PDF pipeline](https://github.com/docling-project/docling/blob/v2.150.0/docling/pipeline/standard_pdf_pipeline.py)) |
| **MinerU `4.2.1`** | `parse()` → `MinerUParser` routes/normalizes input → PDF analysis chooses a tier/parse route → native text and/or rendered-page layout, OCR, formula/table models and VLM work → `ModelJson` → shared postprocessing to versioned `MiddleJson` → renderer/package/API or document library. | Explicit quality/effort tiers and a shared postprocessed schema that supports multiple renderings and product surfaces. The PaddleOCR notes surfaced `v3.7.0` as a release and use PaddleX 3.7 documentation/configuration, but the wrapper and version3.x docs cited here are on moving `main` branches. ## Layout and reading order are separate inferences

All four systems separate, to varying degrees, the job of locating regions from the jobs of obtaining text, assigning text to regions, and deciding an order. A layout model’s “paragraph” or “table” box is a proposal, not a completed document structure; geometry sorting alone is fragile on multi-column pages, sidebars, captions, footnotes, and floating figures. The distinction is especially visible in Docling: its standard pipeline connects preprocessing to layout inference, OCR, layout cleanup, table recognition, page assembly, then applies reading-order and hierarchy work after page integration. Its standard options enable OCR and table structure by default, but its PDF-aware OCR mode can avoid re-recognizing clusters containing only native PDF text. ([pipeline source](https://github.com/docling-project/docling/blob/v2.150.0/docling/pipeline/standard_pdf_pipeline.py), [pipeline options](https://github.com/docling-project/docling/blob/v2.150.0/docling/datamodel/pipeline_options.py), [reading-order model](https://github.com/docling-project/docling/blob/v2.150.0/docling/models/stages/reading_order/readingorder_model.py))

MinerU’s PDF route is tier-dependent: its Flash/text route can use native analysis without the hybrid inference route, while higher-effort routes add small-model layout, OCR and, at High/Xhigh, VLM processing. Its window analysis and postprocessing yield page blocks and geometry; layout proposal, block ordering, and cross-page normalization remain different concerns. Marker makes page-level text acceptance explicit: it can use PDF character-stream positions for accepted native-text pages, while scanned or unreliable pages depend more on model ordering and OCR. Its `fast` and `balanced` modes change the amount and kind of visual/model work, rather than representing two interchangeable names for the same path. ([MinerU PDF pipeline](https://github.com/opendatalab/MinerU/blob/mineru-4.2.1-released/mineru/backend/analysis/pdf/pipeline.py), [Marker line builder](https://github.com/datalab-to/marker/blob/v2.1.0/marker/builders/line.py), [Marker layout builder](https://github.com/datalab-to/marker/blob/v2.1.0/marker/builders/layout.py))

PP-StructureV3’s public contract exposes layout blocks and a parsing-result list documented in reading order, plus OCR text/polygons/scores. Its technical report describes region grouping and document-level order recovery as distinct from OCR and layout detection. The reviewed sources do not establish a native PDF text-first path that preserves PDF character geometry as primary evidence: PDFs are ordinarily processed as rendered pages. This makes the architecture a natural fit for image/scanned-page workflows, but means born-digital PDFs should be evaluated against a native-text-first route rather than assumed to benefit from re-OCR. PaddleOCR-VL is a separate VLM parsing route; do not attribute its behavior to PP-StructureV3. ([PP-StructureV3 guide](https://paddlepaddle.github.io/PaddleX/3.7/en/pipeline_usage/tutorials/ocr_pipelines/PP-StructureV3.html), [PaddleOCR 3.0 report](https://arxiv.org/abs/2507.05595))

## Table recognition and output models show the key tradeoffs

Tables illustrate why “parser supports tables” says too little. Docling has a dedicated table-structure stage: TableFormer predicts logical cells/grid from a table region and aligns cells with native/OCR text when available. It can retain row/column dimensions, spans and header flags in its structured result. Marker 2.1.0 has no dedicated neural table-structure model in its default processor: for digital PDFs it applies deterministic grid heuristics to positioned PDF text and characters; scanned or low-confidence tables can use Surya crop recognition to return HTML. MinerU combines native table recovery and specialized recognition according to suitability and analysis tier, with VLM fallback in higher-effort routes. PP-StructureV3 has PP-TableMagic/table-recognition routes that can construct HTML from cell/structure output; the effective route depends on configuration, including wired/wireless modes. These are documented implementation distinctions, not a claim that one strategy is most accurate on every table family. ([Docling table model](https://github.com/docling-project/docling/blob/v2.150.0/docling/models/stages/table_structure/table_structure_model.py), [Marker table processor](https://github.com/datalab-to/marker/blob/v2.1.0/marker/processors/table.py), [Marker table reconstruction](https://github.com/datalab-to/marker/blob/v2.1.0/marker/processors/table_recon.py), [MinerU table module](https://github.com/opendatalab/MinerU/blob/mineru-4.2.1-released/mineru/backend/analysis/pdf/tables.py), [PaddleX 3.7 PP-StructureV3 guide](https://paddlepaddle.github.io/PaddleX/3.7/en/pipeline_usage/tutorials/ocr_pipelines/PP-StructureV3.html))

Each project also preserves a different kind of canonical or semi-canonical result. Docling’s `DoclingDocument` is a typed hierarchy with text, table, picture and other items, provenance/layout information and ordering; Markdown and HTML are serializers over it. MinerU distinguishes internal `ModelJson` from a shared postprocessed, versioned `MiddleJson` protocol (`docvortex.middle`, schema version `2.0` in the reviewed docs), then offers structured content and asset-aware renderings. Marker’s Pydantic `Document` is a page/block tree with polygons, block types, relationships and HTML/content; Markdown is produced as a renderer projection. PP-StructureV3 exposes page result objects with metadata, ordered parsing results, layout labels/boxes, OCR and specialist structures, alongside convenience serializers. In every case a rendered format is a view: Markdown can flatten spans, omit configured layout labels, or refer to assets stored separately. Preserve the richer result if geometry, provenance, cell spans, or auditability matter. ([Docling document model](https://docling-project.github.io/docling/concepts/docling_document/), [Docling serialization](https://docling-project.github.io/docling/concepts/serialization/), [MinerU result contract](https://opendatalab.github.io/MinerU/reference/output_files/), [Marker document schema](https://github.com/datalab-to/marker/blob/v2.1.0/marker/schema/document.py), [Marker Markdown renderer](https://github.com/datalab-to/marker/blob/v2.1.0/marker/renderers/markdown.py), [PaddleX 3.7 guide](https://paddlepaddle.github.io/PaddleX/3.7/en/pipeline_usage/tutorials/ocr_pipelines/PP-StructureV3.html))

Keep documented behavior distinct from claims about quality. Entry points, configurable modules, result fields, routing logic, and output schemas are described in code or official docs at the versions cited above. Performance and accuracy numbers are a different kind of evidence: Marker’s README reports its own `olmocr-bench` measurements for Marker 2.1.0 modes; PaddleOCR’s 2025 report compares PP-StructureV3 with older pinned competitors (including MinerU 1.3.11, Marker 1.2.3, Docling 2.14.0); and the Docling technical report measures its earlier system on its own test setup. Those results do not establish a current, independent, same-corpus ranking of these four versions. Treat them as publisher-reported or historical benchmark results and reproduce evaluations using the same documents, modes, hardware, and metrics before making a local decision. ([Marker README benchmark section](https://raw.githubusercontent.com/datalab-to/marker/v2.1.0/README.md#benchmarks), [PaddleOCR 3.0 report](https://arxiv.org/abs/2507.05595), [Docling technical report](https://arxiv.org/html/2408.09869v5))

## Fastdocparse already parses structure, but extraction still flattens it

The repository’s current boundary is not simply “no parser.” `src/fastdocparse/parsing/models.py` defines `ParsedDocument`, `ParsedPage`, and `ParsedElement`, with normalized page boxes, nested children, provenance labels, optional confidence, attributes, and relations. `src/fastdocparse/parsing/pdf.py` uses PyMuPDF to extract positioned words, lines, blocks, images and detected table cells; it also has a conservative aligned-text table heuristic and a positioned OCR path for image-only pages. This is a meaningful geometry-aware parse surface, and worth tracing independently. ([models](https://github.com/pranjalparmar/fastdocparse/blob/main/src/fastdocparse/parsing/models.py), [PDF adapter](https://github.com/pranjalparmar/fastdocparse/blob/main/src/fastdocparse/parsing/pdf.py))

The main extraction path is currently narrower. `DocumentParser.extract()` resolves an ingestion handler, which returns `str`; the PDF handler in `src/fastdocparse/ingestion/pdf_ingest.py` calls native text extraction and falls back to rendered-page OCR only when the extracted text is shorter than 30 characters. It then chunks that text, asks the LLM for schema fields, merges chunk results, and grounds/checks field values against text. `docs/architecture.md` describes the same parse-text → schema extraction boundary. Therefore, the richer `ParsedDocument` PDF route is not yet the central evidence object passed through this extraction flow: geometry-aware blocks, table cell grids, images and relations are not the canonical input to extraction. The contrast is useful for learning from the four projects without implying that their full schemas or model stacks should be copied. ([PDF ingestion](https://github.com/pranjalparmar/fastdocparse/blob/main/src/fastdocparse/ingestion/pdf_ingest.py), [parser orchestration](https://github.com/pranjalparmar/fastdocparse/blob/main/src/fastdocparse/parser.py), [architecture guide](https://github.com/pranjalparmar/fastdocparse/blob/main/docs/architecture.md))

## Follow one document through each seam before drawing conclusions

Use a small, repeatable reading sequence rather than trying to absorb each repository at once. Start with the documented entrypoint and pinned/default configuration, then trace one born-digital PDF from input adapter to its final structured result. Follow one scanned page next to see what triggers rendering/OCR, how OCR geometry and text join the layout, and where failure or fallback is reported. Then isolate one table to see whether its grid comes from PDF geometry, a heuristic, a specialist structure model, or a VLM, and how text is assigned to cells. After that, read the canonical model and serializer together to identify what Markdown discards or moves into assets. Finally, inspect tests and fixtures for which behaviors are actually asserted. For PP-StructureV3’s moving `main` links, first pin the checked-out commit; keep the PaddleX 3.7 guide/config as a versioned comparison point.

| Stage | What to follow | Useful first source paths |
|---|---|---|
| **1. Read entrypoint** | Input routing, constructor defaults, and the selected pipeline/mode. | Docling `docling/document_converter.py`; MinerU `mineru/parser/mineru_parser.py` and `mineru/backend/analyze.py`; Marker `marker/converters/pdf.py`; PaddleOCR `paddleocr/_pipelines/pp_structurev3.py`. |
| **2. Follow one PDF** | Native text evidence, geometry, page rendering, and page-level order. | Docling `docling/backend/pdf_backend.py` and `docling/pipeline/standard_pdf_pipeline.py`; MinerU `mineru/backend/analysis/pdf/pipeline.py` and `window.py`; Marker `marker/providers/pdf.py`, `marker/builders/document.py`, `marker/builders/line.py`; PaddleX 3.7 PP-StructureV3 guide/YAML. |
| **3. Follow one scan** | OCR invocation, coordinates, fallback policy, and provenance. | Docling `docling/models/stages/ocr/`; MinerU `mineru/backend/analysis/pdf/ocr.py`; Marker `marker/builders/ocr.py`; PaddleOCR wrapper plus configured OCR/layout modules. |
| **4. Follow one table** | Table region detection, grid/cell recognition, text alignment, spans, and failure behavior. | Docling `docling/models/stages/table_structure/table_structure_model.py`; MinerU `mineru/backend/analysis/pdf/tables.py`; Marker `marker/processors/table.py` and `table_recon.py`; PaddleX guide/config and PP-StructureV3 table result fields. |
| **5. Follow serializer** | Canonical document model versus Markdown/HTML/JSON and sidecar assets. | Docling serialization docs and `docling-core` types; MinerU output contract; Marker `marker/schema/document.py` and `marker/renderers/`; PaddleX result save methods. |
| **6. Follow tests** | Golden fixtures, asserted contracts, and known edge cases—then compare results on one fixed local sample. | Read each upstream repository’s tests for the relevant pipeline/model; in fastdocparse start with [`tests/test_document_model.py`](https://github.com/pranjalparmar/fastdocparse/blob/main/tests/test_document_model.py), [`tests/test_parser.py`](https://github.com/pranjalparmar/fastdocparse/blob/main/tests/test_parser.py), and [`tests/test_receipt_and_ctdar_benchmarks.py`](https://github.com/pranjalparmar/fastdocparse/blob/main/tests/test_receipt_and_ctdar_benchmarks.py). Benchmark numbers should be compared only where data, versions, modes, hardware and metrics match. |

This sequence answers “how does it work?” without turning the investigation into an implementation mandate. A test passing proves that a chosen assertion holds for its fixture; it does not prove general document quality. A benchmark score similarly speaks to a particular dataset and configuration. **No parser produces guaranteed perfect structure**: native text may be corrupted or oddly ordered, OCR can miss or alter content, layout can merge/split regions, and table recognition can misplace text or spans. The useful outcome is a map of where evidence enters, which stages infer relationships, what the result preserves, and where errors can be inspected.

## Conclusion

These codebases support a practical comparative study because their differences are architectural and traceable: evidence policy, recognition route, table strategy, and output model are all visible in source. For fastdocparse, the most productive result is a clearer view of the existing seam between a geometry-aware parse representation and the text-only evidence currently used by the principal extraction flow. Understanding that seam—and the losses introduced by each serializer—will make later design decisions more grounded, without requiring adoption of any parser’s full pipeline or accepting an unverified winner claim.
